Chapter 13. Getting unstuck alone

Sooner or later your screen will show something this guide didn't, and this is the chapter to open when it does. It has a method for finding the cause, notes on reading what kubectl, cilium and hubble print, a ladder of four questions for the most common problem in this lab, one service that can't reach another, and a table of every failure met while the guide was tested. Then you break the lab three times on purpose and repair it, so the first time you meet these errors is on a day when you know the answer. The chapter ends with a full rebuild from nothing. Plan about 1.5 hours for reading and another 1.5 hours for the drills and the rebuild.

The method, in five moves

Follow these in order every time. Most problems end at the first or second move.

  1. Read the exact error. Copy the whole message instead of going from memory. A Python program puts the real error on the last line of its message. kubectl usually starts its message with error: or Error from server. When you have the text, look for it first in the failure block of the step you were on, then in the table further down this chapter.
  2. Find the layer. A layer is one level of the stack the lab is built from. From the bottom up those are Windows and WSL, then Docker, then Kubernetes, then your apps, and on top of everything your policies. The program that printed the message tells you the layer. A message from wsl or about memory belongs to the bottom. One starting with docker: belongs to Docker. A pod stuck in a strange STATUS belongs to Kubernetes, a Python traceback to an app, and a Policy denied line in Hubble to your policies. Fix the lowest broken layer first, because everything above it depends on it.
  3. Compare with the last state that worked. git status lists the files you changed since your last commit, and git diff shows exactly which lines changed. git log --oneline lists your commits, newest first, and git diff <commit> -- <file> shows how a file differs from the version in that commit. git restore <file> throws away your unstaged changes to that file. If you already ran git add, use git restore --staged --worktree <file> to return it to the last commit. This can't be undone, so if the changes might be worth keeping, copy the file first, for example cp k8s/app.yaml ~/app.yaml.bak. If the output of git diff or git log fills the screen and a : or (END) appears at the bottom, use the arrow keys to scroll and press q to return to the prompt.
  4. Change one thing, then run the same check again. Two changes at once leave you not knowing which one helped, or which one broke something else.
  5. Rebuild from scratch as the last resort. The last part of this chapter shows how, and it takes about 15 minutes.

How to read the tools' output

Each tool puts the part you need in a different place.

Pods: kubectl get pods

kubectl -n campus get pods prints one line per pod. The READY column shows how many of the pod's containers passed their readiness probe, the regular check Kubernetes makes to see whether a container can take traffic. 1/1 is healthy. 0/1 means the container exists but isn't ready, even if STATUS says Running, and then the pod gets no traffic. The STATUS column should say Running. ContainerCreating is normal for a few seconds after a start, Pending means no node has accepted the pod, and CrashLoopBackOff means the program keeps crashing and Kubernetes waits longer before each new attempt. ErrImageNeverPull means the image isn't on the node. RESTARTS counts how often the container was restarted, and a number that keeps rising is a crash you need to read in the logs. Add -o wide to see which node each pod runs on.

Events: kubectl describe pod and kubectl get events

An event is a short note Kubernetes writes when something happens to an object, such as a pod being placed on a node or an image failing to load. kubectl -n campus describe pod <pod-name> prints everything about one pod and ends with its events. Read that list from the bottom up, because the newest event is at the bottom and usually names the problem. The reasons you'll meet most are FailedScheduling, where no node fits the pod, BackOff, where a container keeps crashing, Unhealthy, where the readiness probe failed, and Failed, often with the image name in the message. kubectl -n campus get events --sort-by=.lastTimestamp shows the events of the whole namespace in time order, newest at the bottom. Kubernetes deletes events after about an hour, so an old problem may have no events left.

Logs: kubectl logs

kubectl -n campus logs deploy/api prints what the api program wrote while it ran. If the container crashed and was restarted, the interesting log belongs to the container that died, and --previous shows that one. A Python error appears as a traceback, the list of function calls that led to the error. Read it from the last line up. The last line names the error type and its message, for example a KeyError or a connection error. Above it, find the lowest line that starts with File "/app/ and names one of your own files. That's the line of your code where things went wrong.

Cilium: cilium status

cilium status prints a block at the top with one line each for Cilium, the Operator, Envoy and Hubble Relay. All of them must say OK. Below that, any line with errors or not ready names a pod. While Cilium is starting, for example during setup.sh, red error lines and pods of DaemonSet cilium are not ready appear for a minute or two, and that's normal. Judge only the final block.

Hubble: hubble observe

Chapter 11 covers Hubble line by line. When you're hunting a problem, read the verdict first, FORWARDED or DROPPED. Then read the drop reason. Policy denied points at your policies, and any other reason points lower down the stack. On the decision line, EGRESS or INGRESS tells you whether the sender's policy or the receiver's said no.

The four-question ladder

Most trouble in this lab looks the same: some service X can't reach some service Y. The portal shows an error, or check-portal.sh prints FAIL.

Each portal check travels a chain of services. portal page loads goes from outside the cluster to frontend. news list has 3 items goes from frontend to news. sara can log in goes from frontend to api, then from api to auth and from auth to db. sara sees her profile and sara sees her 2 grades go from frontend to api, then from api to auth and from api to db. ops can open the admin panel goes from ops to admin and from admin to db. Climb the ladder for each hop in the chain, the first hop first, with X as the sender and Y as the receiver. The sender of the first hop of portal page loads sits outside the cluster, so only questions 1 and 2 apply to it.

Start with question 1 and work down the list. Stop at the first question whose answer is no.

  1. Is Y running and ready? Run kubectl -n campus get pods -l app=<Y>. The pod must be 1/1 Running. If it isn't, the problem is in Kubernetes or in Y's program, so read its events and its logs.
  2. Does Y answer inside its own pod? Run kubectl -n campus exec deploy/<Y> -- bash -c "timeout 2 bash -c 'echo > /dev/tcp/127.0.0.1/<port>' && echo answers". This opens a connection from Y to itself, which never crosses a pod boundary, so no policy can block it. Replace <port> with Y's port from the chapter 1 services table: frontend 80, news 5000, api 8080, auth 5001, db 5432, admin 5002. If answers doesn't appear, Y's program isn't listening on that port, and the fix is in Y's code or its settings.
  3. Does the name resolve from X? Run kubectl -n campus exec deploy/<X> -- timeout 10 getent hosts <Y>. getent hosts looks a name up the same way programs do and prints the address it found, and timeout 10 stops it after 10 seconds. If DNS is blocked, the command waits the full 10 seconds and then prints nothing. No output means DNS failed, and in this lab that almost always means the allow-dns policy is missing or broken.
  4. Is the path from X to Y free of drops? Run hubble observe --to-pod campus/<Y> --verdict DROPPED --last 10. If you see Policy denied lines from X, the answer is no, and the decision line tells you which policy to open. EGRESS DENIED means X's own policy has no egress rule toward Y. INGRESS DENIED means Y's policy has no ingress rule from X.

If all four answers are yes and it still fails, compare the port X uses with the Service's port in k8s/app.yaml. Drill 1 below climbs the whole ladder on a real failure.

Two words in the table need a sentence each. A line ending is the invisible character at the end of every line of a text file. Linux uses one, called LF, and Windows uses two, CR followed by LF. Bash reads the extra CR as part of the command, and that's where the \r and ^M in those messages come from. A rate limit is a cap on how many requests a service accepts from one sender in a period of time.

The Docker DNS fix from chapter 5 is two commands in Ubuntu. Run echo '{"dns": ["8.8.8.8", "1.1.1.1"]}' | sudo tee /etc/docker/daemon.json, which creates the file, or replaces it if it exists, since /etc/docker belongs to root and only sudo may write there. A fresh Docker Engine doesn't have this file, so nothing is lost. Then run sudo systemctl restart docker. The restart also stops the three cluster containers, so wait a few minutes until kubectl get nodes shows all three nodes Ready.

Before the drills, a health check

Each drill breaks one thing on purpose, so the lab has to be healthy when you start, or a break you didn't make will pass for the one you did. If Windows restarted since chapter 12, follow "After a Windows restart" near the end of this chapter first. Then run this.

hubble status | grep Connected keeps only the line about connected nodes. The && between the parts runs each one only if the one before it succeeded.

You should see three lines.

They must read Connected Nodes: 3/3, then PORTAL: 6/6 OK, then 10.

If you see this instead

The Hubble port-forward isn't running. Start it with cilium hubble port-forward &, wait five seconds and run the check again.

The portal line reads less than 6/6 OK. The lab is already broken. Climb the four-question ladder for the failing check before you start any drill.

The last number isn't 10. Apply your policies with kubectl apply -f k8s/policies/, wait ten seconds and run the check again.

Drill 1: auth stops accepting api

This drill breaks one label in one policy and makes you find it with the ladder, as if you didn't know what you'd changed. It needs a clean state, so finish chapter 12's commit first.

The auth policy selects its pod with app: auth. Change that one value, and the policy no longer applies to the auth pod. Default deny then covers auth on its own. No other pod may connect to it, only the node's readiness probes through allow-kubelet-probes, and auth may no longer reach db.

sed -i edits the file in place. The part between the quotes says "replace this with that". ^ means the start of a line and $ its end, so the pattern only matches a line holding exactly six spaces and app: auth. Only the auth policy's own endpointSelector has six spaces there. The two other app: auth lines, in the api policy's egress and in the db policy's ingress, have eight spaces and stay as they are. git diff then shows what changed.

You should see a short diff of k8s/policies/2-allow.yaml.

It shows one line removed, marked with -, holding app: auth, and one line added, marked with +, holding app: auth-broken. Nothing else may be listed.

Apply the broken file.

You should see one line per policy in the file.

The auth line must say configured and the other six unchanged.

Run the checks a real user would make. The sleep 8 gives Cilium a few seconds to update every pod first.

Three checks fail.

sara can log in, sara sees her profile and sara sees her 2 grades say FAIL, and the last line reads PORTAL: 3/6 OK. Lines starting with jq: may appear between them. They come from the script trying to read an error page as JSON, and they're part of the same failure. All three go through auth, which api asks to check the password or the token. Here is the symptom a user would report: "the portal page loads but I can't log in". Pretend you don't know the cause, and climb the ladder with X as api and Y as auth.

Question 1, is auth running and ready?

-l app=auth keeps only pods carrying that label.

There's one auth pod and it's 1/1 Running, so go on to question 2.

Question 2, does auth answer inside its own pod?

kubectl exec deploy/auth -- runs the command after -- inside the auth pod. /dev/tcp/127.0.0.1/5001 is a bash feature that opens a TCP connection when you write to it, here to port 5001 on the pod itself. timeout 2 gives up after two seconds. If the connection opens, && runs the echo.

It prints auth answers, so the auth program is listening on 5001.

Question 3, does the name auth resolve inside api?

You get one line with an address starting with 10.96. and the full name auth.campus.svc.cluster.local, so DNS works.

Question 4, is the path from api to auth free of drops? Save the answer, since it makes a good example for your report.

The answer is no. Here's the cause. The lines run from campus/api- to campus/auth- on port 5001, in pairs, with Policy denied DROPPED. Look at the decision line of a pair. It says policy-verdict:none INGRESS DENIED. Api was allowed to send, since its own policy has egress to app: auth. Auth was not allowed to receive, because no policy selects the auth pod with an ingress rule any more. The word INGRESS sent you to the receiver's policy, and there you find auth-broken. If you'd checked the labels with kubectl -n campus get pods --show-labels, you'd have seen that no pod carries app=auth-broken.

Repair it from Git and check the portal.

git restore puts the file back exactly as it was in your last commit. Applying it again changes the auth policy back.

The auth line says configured again, and the last line must read PORTAL: 6/6 OK.

If you see this instead

git diff prints nothing after the sed command. Run git status first. If k8s/policies/2-allow.yaml is listed under Untracked files, it was never committed. Open it, change auth-broken back to auth, commit it with git add -A && git commit -m "add policies" and start the drill again. Otherwise the pattern matched no line, which means your file's spacing differs from the tested one. Open k8s/policies/2-allow.yaml in VS Code, find the policy named auth, change app: auth under its endpointSelector to app: auth-broken by hand and save. Then compare the rest of that file with chapter 10, because a spacing difference elsewhere may hide a real mistake.

The portal still shows PORTAL: 6/6 OK after the broken file was applied. Either the apply didn't say configured, or Cilium needed a little longer. Run the apply and the check again.

The file was never committed, so Git has nothing to restore it from. Edit auth-broken back to auth by hand, apply the file, and then commit it with git add -A && git commit -m "add policies" so this can't happen again.

Drill 2: no more name lookups

Every pod needs DNS to find the others by name. This drill deletes the allow-dns policy and shows how widely that one deletion breaks the portal, and how Hubble names the cause at once.

kubectl delete cnp allow-dns removes one policy by name. Default deny now blocks every DNS question from every pod in campus.

You should see one line confirming the deletion.

It reads ciliumnetworkpolicy.cilium.io "allow-dns" deleted from campus namespace.

Wait a little longer this time before checking, because nginx remembers each answer it got for 10 seconds.

The checks take longer than usual, since each one waits up to five seconds for a name that never resolves.

Only the first check, portal page loads, still passes, so the last line reads PORTAL: 1/6 OK. The page itself is a file nginx serves without looking up any name. The ops check may also print command terminated with exit code 28, which is curl inside the ops pod giving up after its time limit. Five checks broke from one cause, so go straight to question 4 of the ladder and look for drops on port 53, the DNS port.

--port 53 keeps flows where either end uses port 53.

Every line goes from a campus pod to a kube-system/coredns- pod on port 53, with EGRESS DENIED on the decision lines and Policy denied DROPPED on the drop lines. The senders differ, frontend and ops among them, but the destination is always the same. When many pods fail at once and all their drops go to one place, look for a policy every pod shares.

Put the policy back and check.

allow-dns says created, the other two say unchanged, and the last line must read PORTAL: 6/6 OK.

If you see this instead

allow-dns was already gone before you started, so your lab was broken before the drill. Apply k8s/policies/1-baseline.yaml, check for PORTAL: 6/6 OK, and start the drill again.

The portal checks still say PORTAL: 6/6 OK after the deletion. You checked within nginx's 10 seconds, or the deletion failed. Wait 15 seconds and run bash check-portal.sh again.

After the repair the count is below 6. Some programs wait a few seconds before they try a failed lookup again. Wait 15 seconds and run the check again before you look further.

Drill 3: an image that doesn't exist

A typing mistake in an image tag is common, and when it happens Kubernetes can't start the new pod, so the error only shows up in the pod's STATUS and its events. It also shows that Kubernetes keeps the old pod serving while a broken update fails.

kubectl set image changes the image of one container in a Deployment, here the container named auth, to campus-app:1.1. That tag was never built, and the Deployment uses imagePullPolicy: Never, so Kubernetes won't try to download it either. The change starts a rollout, the way Kubernetes replaces a Deployment's pods with new ones.

You should see a single line.

It reads deployment.apps/auth image updated.

There are two auth pods now. The old one is still 1/1 Running, while the new one shows 0/1 and ErrImageNeverPull. Its name has a different middle part, because it belongs to the new version of the Deployment.

Find the reason in the events.

--sort-by=.lastTimestamp orders the events by time, and tail -5 keeps the five newest.

Look for a Warning line about the new auth pod whose message reads Container image "campus-app:1.1" is not present with pull policy of Never. That names the problem exactly, an image tag the node doesn't have.

Check the portal while the broken pod sits there.

It still reads PORTAL: 6/6 OK. A rollout keeps the old pod running until a new one is ready, and this new one never gets ready, so the old one keeps serving. Your users wouldn't notice. Undo the change.

rollout undo returns the Deployment to its previous version, the one with campus-app:1.0. rollout status waits until the Deployment is back in order.

You see deployment.apps/auth rolled back, then deployment "auth" successfully rolled out, then one auth pod, 1/1 Running.

If you see this instead

The new pod shows ContainerCreating instead of ErrImageNeverPull. Kubernetes hasn't tried the image yet. Wait a few seconds and list the pods again.

The name before the = in the set image command must be the container's name, auth. Check for a typo and run it again.

After the undo, two auth pods are still listed. The broken one is shutting down. Wait a few seconds and list the pods again.

After a Windows restart

Restarting Windows stops WSL, and with it everything you started by hand. Docker starts again with Ubuntu, and the cluster's three containers come back up with it. The Hubble port-forward, the Hubble UI and your dashboard don't. Open Ubuntu and check the cluster first.

--format prints only each container's name and status, one per line.

You should see three lines, one for each node.

kind-control-plane, kind-worker and kind-worker2 must each say Up, followed by how long they've been running. Run cd ~/microseg, then kubectl -n campus get pods every half minute until all seven pods show 1/1 Running. Then start the helpers again. Run cilium hubble port-forward & for Hubble. Start the dashboard in a second terminal with cd ~/microseg/dashboard && ../.venv/bin/python app.py, and the Hubble UI, if you need it, with cilium hubble ui --open-browser=false &. Finish with bash check-portal.sh, whose last line must read PORTAL: 6/6 OK.

If you see this instead

The list is empty, or a node says Exited. Start them with docker start kind-control-plane kind-worker kind-worker2 and wait two minutes. If the portal still fails after that, rebuild from scratch as described next.

Rebuild from scratch, the last resort

When nothing else helps, or you can't tell any more what you've changed, rebuild. Your files in ~/microseg are untouched by this. Only the cluster is thrown away and built again from them. Do it once now as a drill, so you know it works and how long it takes on your laptop before you need it in an emergency.

kind delete cluster removes the three node containers and everything inside them. bash setup.sh creates the cluster and installs Cilium as in chapter 4, and bash deploy.sh builds and loads your images and deploys the portal as in chapter 6. && starts each command only if the one before it succeeded, so a failure stops the chain where it happened. Expect about 15 minutes. While cilium status --wait runs, red error lines appear for a while, and that's normal.

You should see the output of all three scripts, ending with the pod list from deploy.sh.

The last lines show seven pods, all 1/1 Running, with frontend and news on kind-worker and the rest on kind-worker2. The rebuilt portal is a flat network with a fresh database, because deploy.sh never applies policies. Apply them, and restart the Hubble port-forward, since the old one died with the old cluster.

pkill -f "hubble port-forward" stops any port-forward still left from before. It prints nothing, whether or not it found one. If the old port-forward was started in this terminal, bash prints a line ending in Terminated for it, which is expected. The next line starts a new one in the background, and hubble status checks it. The Hubble UI stopped with the old cluster too, so start it again with cilium hubble ui --open-browser=false & when you need it.

Ten policies say created, and the Hubble part must show Connected Nodes: 3/3. The line starting with [1] is bash telling you the job number and process number of the background port-forward, and yours will differ.

If you see this instead

kind delete cluster didn't run or didn't finish. Run kind delete cluster on its own, wait for the prompt, then run the full rebuild line again.

setup.sh stops after cilium status --wait has waited 15 minutes and still reports errors. It may end with a long crash dump that starts with fatal error: all goroutines are asleep - deadlock!, which only means the waiting ran out of time. Usually Cilium's images are still downloading. Don't repeat the rebuild, because kind delete cluster throws the finished downloads away. Follow the same failure in chapter 4's setup.sh step, which checks the pods with kubectl -n kube-system get pods and finishes the setup by hand. Then run bash deploy.sh, which the stopped chain never reached. If it fails the same way twice, go to appendix A that same day.

toomanyrequests appears while setup.sh pulls nginx:1.28 or postgres:17. Docker Hub is limiting downloads from your address. See its line in the table above.
