Chapter 1. What you will build

You type no commands in this chapter. It's the lab on paper, and by the end you should be able to sketch the portal's 7 programs on their nodes and write down, without looking, the 8 flows between them that stay open once segmentation is on. That sketch is the checkpoint. Plan on about 45 minutes.

Where everything runs, layer by layer

Everything in the lab runs on your one laptop, stacked in layers. Windows 11 runs WSL 2, a light virtual machine with a real Linux kernel, and Ubuntu 24.04 lives inside it. Ubuntu runs Docker Engine, which holds three containers that each pretend to be a whole machine. Those containers are your three Kubernetes nodes, kind-control-plane, kind-worker and kind-worker2, and they run the pods of the portal in the namespace campus, next to Cilium's own pods in the namespace kube-system.

In Figure 2, look at where kubectl, cilium and hubble sit. They run in Ubuntu itself, outside the cluster, and reach into it from there.

Not every program in this project lives inside the cluster. The table lists what you'll open or run and where it lives.

What Where it runs How you reach it
the Campus Portal seven pods in the namespace campus http://localhost:30080 in your Windows browser, or from the Ubuntu terminal
the Hubble UI Cilium's pods, opened by cilium hubble ui in the Ubuntu terminal http://localhost:12000
your dashboard (chapter 7) a Python program in Ubuntu, outside the cluster http://localhost:5050
kubectl, cilium, hubble Ubuntu the Ubuntu terminal
the five attack commands (chapter 8) Windows PowerShell, using curl.exe they go in through localhost:30080, like any visitor

Your Windows browser can open localhost:30080 because of two forwarding steps. A port mapping is a rule that passes connections arriving on a port of one machine to a port of another. Docker holds a port mapping that passes port 30080 in Ubuntu on to port 30080 of the kind-worker container, and WSL passes localhost ports from Windows into Ubuntu. Follow one request from your browser to the portal and it goes like this.

  1. The browser connects to localhost:30080 on Windows.
  2. WSL hands the connection to Ubuntu, still on port 30080.
  3. Docker's port mapping, which kind-config.yaml asks for, passes it to port 30080 on the node kind-worker.
  4. On kind-worker, port 30080 is the NodePort of the Service frontend, so Kubernetes passes it to the frontend pod on port 80.

The port mapping listens on 127.0.0.1 only, the address a machine uses for itself, so other people on your Wi-Fi can't open your portal.

The portal's architecture

The portal has exactly one door from the outside, NodePort 30080 on kind-worker. Every other program has a name and a port that work only inside the cluster.

Figure 3 puts the seven pods on their two worker nodes, with one arrow coming in at NodePort 30080. The node kind-control-plane runs none of them.

The frontend and news pods, the public-facing part of the portal, run on kind-worker, and the other five (api, auth, db, admin and ops) run on kind-worker2. The node labels tier=frontend and tier=backend decide that placement. Placement alone neither grants nor blocks any connection.

All of the portal's Kubernetes objects live in the namespace campus, and there are four kinds of them.

Object How many Names What it's for
Secret 1 db-credentials the database user, password and database name
ConfigMap 2 frontend-files, db-init the nginx settings and portal page, and the SQL that fills the database
Service 6 frontend, news, api, auth, db, admin a fixed name and port for each program that something calls
Deployment 7 frontend, news, api, auth, db, admin, ops keeps one pod of each program running

A ConfigMap is a Kubernetes object that holds files or settings and hands them to a pod, which sees them as ordinary files. That lets nginx and PostgreSQL run from stock images while your own files are slipped in from outside. A Secret is the same idea for passwords.

The Secret db-credentials holds POSTGRES_USER=postgres, POSTGRES_PASSWORD=postgres and POSTGRES_DB=campus. The db pod reads the Secret to set itself up, and api, auth and admin read it to log in. News never gets it. The common password postgres is there on purpose, because in step 3 of the attack the intruder guesses it.

k8s/app.yaml holds the Secret, the Services and the Deployments. deploy.sh creates the two ConfigMaps straight from the files in frontend/ and db/. You write k8s/app.yaml and deploy.sh in chapter 6, and the files in frontend/ and db/ in chapter 5.

The 7 programs

Four of the programs are written in Python with Flask, a small Python library for building web services. Each one is started by gunicorn, a program that runs a Flask service as a web server and keeps two copies of it ready for requests. The image campus-app:1.0 holds all four programs. Api, auth and admin run from it, and each of their Deployments picks which program to start. Ops uses it too, as a place to run commands. News gets its own image, campus-news:1.0, which is campus-app:1.0 plus the attacker's tools psql and nc. Frontend and db use stock images.

Program Image Port Node What it does Called by, after segmentation
frontend nginx:1.28 80, NodePort 30080 kind-worker sends the portal page to the browser and passes /api/ requests to api and /news requests to news your browser (world)
news campus-news:1.0 5000 kind-worker lists 3 announcements and runs the image link checker, which has the command injection bug frontend
api campus-app:1.0 8080 kind-worker2 login, profile and grades for logged-in students, plus the forgotten /api/export frontend
auth campus-app:1.0 5001 kind-worker2 checks passwords, hands out login tokens and says which student owns a token api
db postgres:17 5432 kind-worker2 the PostgreSQL database campus, with students, grades and sessions api, auth, admin
admin campus-app:1.0 5002 kind-worker2 internal admin panel that lists every user, with no login ops
ops campus-app:1.0 none kind-worker2 stands in for the IT team's maintenance machine. It runs sleep infinity, which waits forever, so there's a pod you can run commands in nobody

Ops has a Deployment but no Service, because nothing ever calls it. It only makes calls.

The 8 allowed flows

A flow is one kind of connection the lab allows, from one program to another on one port. Once segmentation is on, the lab allows exactly the 8 flows below and refuses everything else. You'll use this table twice more. Chapter 9 rebuilds it from what Hubble records, and chapter 10 turns each row into policy rules.

In Figure 4 each arrow is one allowed flow, and no arrow starts at news or at db.

# From To Port Extra rule Why the portal needs it
1 your browser (world) frontend 80, through NodePort 30080 students open the portal
2 frontend api 8080 only GET /api/grades, GET /api/profile and POST /api/login the page logs students in and shows their profile and grades
3 frontend news 5000 the page shows the announcements, and editors use the image checker
4 api auth 5001 api passes each login to auth, and asks auth who owns the token on every profile and grades request
5 api db 5432 api reads the profile and grades rows
6 auth db 5432 auth checks passwords and stores and looks up tokens
7 admin db 5432 the admin panel reads the user list
8 ops admin 5002 IT staff open the admin panel

Flow 2 is the only one with an L7 rule, the one in the Extra rule column. Envoy reads every request on it and lets three kinds through. Anything else, /api/export included, comes back as 403 Forbidden.

Two more kinds of traffic are allowed, and they don't count among the 8. Every pod may ask kube-dns, the cluster's DNS service, for addresses on port 53, because the programs find each other by name, such as api.campus.svc.cluster.local. That's the full name Kubernetes gives the Service: its name, its namespace, then svc.cluster.local. Inside the namespace the short name api works too, and that's the one the project files use, so you never type the long form. The node may also reach every pod for the readiness checks explained after the API table. Both are set in k8s/policies/1-baseline.yaml.

Rows 2 to 8 each need two rules, egress in the caller's policy and ingress in the callee's policy. Row 1 needs only one, the ingress rule in frontend's policy, because world isn't a pod and has no policy of its own. Row 1 starts at your browser, outside the cluster. The dashboard's matrix in chapter 7 only counts paths that start at a pod, so it covers flows 2 to 8 and shows 7 of its 36 paths open after segmentation.

Everything not in the table is refused. News opens no connection except DNS lookups, and neither does the database. Frontend reaches api but not auth, db or admin, only ops may open the admin panel, and no pod can reach the internet. Chapter 9 writes these refusals down in the deny table.

The database

The database campus has three tables. SQL is the language you use to create tables and ask a database questions. A table is a grid of data, a column is one named field in it, such as username, and a row is one record, such as one student. A primary key is the column whose value is different on every row, so it picks out exactly one row. A foreign key is a column that holds another table's primary key, and that's how a grade points to the student it belongs to. SERIAL means the database numbers new rows for you, 1, 2, 3 and so on.

Here's the grades table, copied from db/init.sql. You'll paste the whole file in chapter 5.

REFERENCES students(id) makes student_id a foreign key. TEXT holds words, INT holds whole numbers, and NOT NULL means the column can never be left empty.

Table Columns What a row is
students id (primary key), username (unique), full_name, email, major, year, password_hash one student
grades id (primary key), student_id (foreign key to students), course, grade one grade in one course
sessions token (primary key), student_id (foreign key to students), created_at one login

A hash is a fixed-length fingerprint computed from a piece of text, made so the text can't be worked back out of it. The column password_hash holds the SHA-256 hash of each password, written as 64 hexadecimal characters, which means each one is a digit from 0 to 9 or a letter from a to f. The plain password is never stored. The same password always gives the same hash, and that's how auth checks a login. It hashes the password you typed and looks for a row with your username and that hash.

db/init.sql fills the tables with four students. Each password is the user name followed by 2026.

id username full_name major year password
1 sara Sara Ahmed Computer Science 4 sara2026
2 omar Omar Khalid Information Security 3 omar2026
3 lina Lina Hassan Software Engineering 2 lina2026
4 yousef Yousef Ali Computer Networks 4 yousef2026

It also adds 8 grades, two per student.

id student_id course grade
1 1 Network Security 91
2 1 Cloud Computing 88
3 2 Network Security 58
4 2 Databases 64
5 3 Network Security 77
6 3 Operating Systems 82
7 4 Network Security 69
8 4 Cloud Computing 73

Look at grade row 3. Its id is 3, its student_id is 2, and student 2 is Omar, so this is his Network Security grade of 58. Step 4 of the attack runs UPDATE grades SET grade = 95 WHERE id = 3, which picks the grade row with id 3. It doesn't touch student 3, Lina. Two different tables each have an id 3, so keep them apart.

The sessions table starts empty. Each login adds a row to it. The db pod keeps its data inside its own container, with no persistent volume to survive a restart. Restarting the db pod therefore puts every grade back to its starting value and throws away every login. Chapter 8 uses that to reset the lab after an attack.

The API, endpoint by endpoint

An endpoint is one method and path that a program answers, such as GET /api/grades. Most endpoints here answer with JSON, a plain-text format for data that looks like {"token": "..."}, with names in quotes and values after the colons. A token is a long random string that auth hands you when your password is right. You send it back with each later request in a header, a named line of extra information sent with an HTTP request before its body. This one reads Authorization: Bearer <token>, and it proves you already logged in. Auth's tokens are 32 hexadecimal characters long. A 401 is the HTTP status code for "you haven't proved who you are", and several endpoints in the table answer with it.

Program Endpoint What it needs What it answers
frontend GET / nothing the portal page, index.html
frontend any path starting /api/ whatever api needs passes the request to api unchanged and returns api's answer
frontend any path starting /news whatever news needs passes the request to news unchanged and returns news's answer
news GET /news nothing a JSON list of the 3 announcements
news POST /news/check-image a form field url plain text starting HTTP status of image:. This is the endpoint with the command injection bug
api POST /api/login JSON with username and password passes it to auth and returns auth's answer, {"token": ...} or a 401 error
api GET /api/profile a token your id, full_name, email, major and year, or 401 not logged in
api GET /api/grades a token a list of your grades, each with course and grade
api GET /api/export nothing at all every grade of every student with their full name. An old debug endpoint that nobody removed
auth POST /login JSON with username and password {"token": ...}, or 401 wrong username or password
auth GET /verify a token {"student_id": ...}, or 401 invalid token
admin GET / nothing one line of text naming the /users endpoint
admin GET /users nothing at all every student with id, username, full_name, email and password_hash
db port 5432 user name and password PostgreSQL's own protocol, which psql and the Python programs speak

News, api, auth, admin and frontend also answer GET /healthz with the text ok. That endpoint is for the readiness probe, a check that Kubernetes repeats from the node to decide whether a pod is ready to receive traffic. Until the check passes, the pod shows 0/1 in the READY column and its Service sends it nothing. The db pod runs PostgreSQL's own check, pg_isready, instead of an HTTP request.

Three endpoints in that table are the weak spots the attack in chapter 8 uses. POST /news/check-image is the attacker's way in. GET /api/export gives away every grade to anyone who asks. GET /users on admin hands out every password hash, because the panel trusts that only insiders can reach it.

The portal's six checks

check-portal.sh, which you write in chapter 6, tests the portal the way a student uses it, with six checks. It checks that the page loads, that the news list has 3 items, that sara can log in and gets a 32-character token, that her profile says Sara Ahmed and that she sees 2 grades. The sixth check runs a request from ops to the admin panel and expects 4 users. When all six pass it prints PORTAL: 6/6 OK, and you run it after every change to the policies, to prove real users still get through.

Checkpoint: write the flow table from memory

Checkpoint. Close this guide or turn the page over. In your notebook, draw a table with the columns From, To, Port and Extra rule, then write down every flow the lab allows after segmentation. Leave out DNS and health checks. Then compare your table with the one in "The 8 allowed flows". Your table matches when it has exactly 8 rows with the same From, To and Port. For row 1, 80 counts as a match, and so does 80 through 30080, but 30080 alone doesn't, because the policy is written for port 80 on the pod. The Extra rule column stays empty in every row except frontend to api, which names the three allowed requests, GET /api/grades, GET /api/profile and POST /api/login. If any row differs, find out why that flow is or isn't needed, using the "Why the portal needs it" column. Then take a ten-minute break and try again until you get all 8 without looking.
