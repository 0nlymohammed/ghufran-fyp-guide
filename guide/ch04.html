Chapter 4. Create the cluster

At the end of this chapter you have a three-node Kubernetes cluster running inside Docker, with Cilium as its network plug-in, Hubble recording every connection, and the Hubble web page open in your Windows browser. You'll also run Cilium's own test suite against it. That test is the day-1 go/no-go: if it passes, Cilium works on your laptop and the rest of the guide can be built on top of it. Plan on about 2 hours, because the test alone can run for up to an hour.

Write kind-config.yaml, the shape of the cluster

A cluster is a group of machines that Kubernetes runs as one system, and each machine in it is a node. kind makes every node a Docker container, so your "machines" are three containers inside Ubuntu. This file tells kind how many nodes to create, which Kubernetes version to put on them, and which port of your laptop leads into the cluster.

Open a new file for it in VS Code from the Ubuntu terminal.

As with check-env.sh in chapter 3, VS Code opens an empty editor named after the file and creates the file when you save. Paste the content below. YAML, the format of this file, uses indentation to show which line belongs to which, so the spaces at the start of each line matter and tabs aren't allowed. Check that the status bar shows LF, then press Ctrl+S.

(1) kind: Cluster and apiVersion: kind.x-k8s.io/v1alpha4 tell kind what kind of file this is and which version of its format it uses. Every kind config starts with these two lines.

(2) disableDefaultCNI: true stops kind from installing its own small network plug-in, kindnet. The network plug-in (CNI) is the program that gives every pod an address and carries its traffic. kindnet knows nothing about CiliumNetworkPolicy, the policy type with HTTP rules that this project depends on, and it has no Hubble. So the cluster starts without any plug-in and you install Cilium instead.

(3) kubeProxyMode: iptables keeps kube-proxy, the Kubernetes part that makes a Service's fixed address lead to the pods behind it, working the standard way. A pod is the smallest thing Kubernetes runs, one or more containers that share a network address, and a Service is a fixed name and address in front of a group of pods. Cilium could take over kube-proxy's job, but this lab leaves it alone.

(4) nodes: lists the three nodes. kind names them after the cluster. The file gives no cluster name, so the cluster is called kind and the nodes become kind-control-plane, kind-worker and kind-worker2, in the order they're listed.

(5) role: control-plane makes the first node the control plane, the part of Kubernetes that stores the state of the cluster and decides which node each pod runs on. Your portal's pods never run there.

(6) image: kindest/node:v1.36.4 is the node image, the container image kind uses for a node, with Kubernetes 1.36.4 inside. kind v0.33.0 would pick Kubernetes 1.37 by default, and Cilium 1.20 doesn't support 1.37 yet, so every node names its image explicitly.

(7) role: worker makes a worker node, a node that runs your pods. The first worker becomes kind-worker.

(8) labels: with tier: frontend puts a label on the kind-worker node. A label is a key: value tag that Kubernetes objects carry. In chapter 6 the frontend and news pods ask for a node with tier: frontend, and the other pods ask for tier: backend. These node labels only decide where pods run. They don't separate anything on the network, and the policies in chapter 10 use the pods' own labels instead.

(9) extraPortMappings: opens a door from your laptop into the kind-worker container. containerPort: 30080 is the port inside the container, where Kubernetes will open the frontend Service in chapter 6 as a NodePort, a Service type that opens the same port on the nodes' own addresses. hostPort: 30080 is the port on Ubuntu's side. listenAddress: "127.0.0.1" makes that port listen only on localhost, so other computers on your Wi-Fi can't reach the portal. WSL's localhostForwarding, which you set in chapter 3, then passes localhost:30080 on to Windows.

(10) The last node is the second worker, kind-worker2, with the label tier: backend. It has no port mapping because nothing outside the cluster talks to the backend directly.

Figure 3 has only one way in from outside. Your browser's request goes to localhost:30080, through the port mapping into kind-worker and on to the frontend pod, and every other service sits behind frontend.

Write setup.sh, the one-time setup script

setup.sh creates the cluster, installs Cilium and Hubble, and copies two stock images into the nodes. You run it once now and again only if you ever rebuild the cluster from scratch. Open a new file with code ~/microseg/setup.sh, paste the content below, check that the status bar shows LF and save it with Ctrl+S.

(1) #!/bin/bash says the file is a bash script. The comment line under it says how to run it.

(2) set -e makes the script stop at the first command that fails. Without it, a failed cluster creation would be followed by an install into a cluster that doesn't exist, and the real error would scroll out of sight.

(3) cd ~/microseg moves into the project folder, so kind-config.yaml and images/ are found wherever you start the script from.

(4) kind create cluster --config kind-config.yaml starts three Docker containers, boots Kubernetes inside them and joins the two workers to the control plane. It also writes a kubectl context, kubectl's saved settings for reaching a cluster, named kind-kind, and makes it the current one, so every kubectl command from now on talks to this cluster. Right after this line all three nodes are NotReady. Kubernetes marks a node ready only once a network plug-in is running on it, and you switched kind's plug-in off in kind-config.yaml.

(5) cilium install --version 1.20.5 installs Cilium 1.20.5 into the cluster. Without --version, the cilium command would install 1.20.3, as you saw in chapter 3. Cilium comes as a Helm chart, a package of Kubernetes objects with settings you can change, and each --set changes one setting. The \ at the end of a line continues the same command on the next line, so these five lines are one command.

(6) --set kubeProxyReplacement=false tells Cilium to leave kube-proxy in charge of Services, matching kubeProxyMode: iptables in the kind file.

(7) --set ipam.mode=kubernetes sets IPAM, IP address management, the job of handing out pod addresses. In this mode Cilium uses the address range Kubernetes gave each node, which is what kind expects.

(8) --set hubble.relay.enabled=true turns on Hubble Relay. Cilium runs on every node and records the connections that pass through that node. Hubble Relay collects those records from all three nodes into one place, so the hubble command and the web page see the whole cluster at once.

(9) --set hubble.ui.enabled=true installs the Hubble web page you'll open at the end of this chapter.

(10) cilium status --wait waits until every part of Cilium reports that it's healthy, and prints the status while it waits. --wait-duration 15m lets it wait up to 15 minutes instead of the default 5, because on an ordinary home or university connection the three nodes need about 10 minutes to download Cilium's images.

(11) docker pull nginx:1.28 and docker pull postgres:17 download the two stock images the portal uses, the nginx web server for the frontend and the PostgreSQL database.

(12) mkdir -p images creates the images folder for image archives. -p means there's no error if the folder already exists. The .gitignore from chapter 2 keeps this folder out of Git, because the archives are large and can always be recreated.

(13) docker image save --platform linux/amd64 --output images/nginx.tar nginx:1.28 writes the image into a single archive file, and the next line does the same for postgres. --platform linux/amd64 saves only the variant of the image built for your processor type, amd64, which is the only variant the nodes need and the only one Docker downloaded. Without it, the archive can list variants that aren't there, and kind fails to load it.

(14) kind load image-archive images/nginx.tar copies the image from the archive into every node. Each node keeps its own image store, separate from Ubuntu's Docker, so an image Docker has isn't automatically available inside the cluster. Loading it here means the nodes never have to download it from Docker Hub themselves. Docker Hub limits how many downloads one address may make without an account, and three nodes downloading the same images use that allowance up faster. Chapter 6 loads your own images the same way.

(15) kubectl get nodes --show-labels lists the nodes with all their labels, as a last look at the result.

Before running anything, check that both files were saved with Linux line endings.

file looks inside a file and names its type.

You should see one line per file.

Neither line may contain the words with CRLF line terminators. If one does, that file was saved with Windows line endings. Open it in VS Code, click CRLF in the status bar, choose LF and save again.

Run setup.sh

The script needs 6 to 15 minutes, most of it while the nodes download Cilium's images and Cilium starts. Run it from the Ubuntu terminal and leave the window open until the prompt comes back. For the first few minutes it prints red error lines. Those are expected, and the text under the output below shows what they look like.

You should see the script end with the node list, one line each for kind-control-plane, kind-worker and kind-worker2, all Ready.

All three nodes must show Ready. kind-worker must carry tier=frontend at the end of its labels and kind-worker2 must carry tier=backend. The ages will differ on your laptop.

On the way there the output is long. kind prints its progress with small pictures, then the cilium command reports what it detected and starts waiting. While it waits, it prints a status block again and again, and for the first minutes those blocks contain red error lines like these.

That's normal while Cilium is starting. A DaemonSet is a Kubernetes object that runs one copy of a pod on every node, so Cilium's agent runs three times, once per node, and the errors only mean those copies haven't finished starting yet. Leave it alone and the blocks stop by themselves once everything is healthy. Then the image downloads and loads run, and the script ends with the node list above.

If you see this instead

A node container started but its systemd never finished booting, almost always because the inotify limits from chapter 3 aren't active. Run sysctl fs.inotify.max_user_watches fs.inotify.max_user_instances and compare with chapter 3. If the values are lower, repeat the inotify step there. Then remove the half-built cluster with kind delete cluster and run bash setup.sh again.

A cluster from an earlier attempt still exists, or another container holds port 30080. Run kind delete cluster, which removes the cluster named kind and its containers, then run bash setup.sh again. If the second message comes back, run docker ps and look in the PORTS column for the container that holds 127.0.0.1:30080, then remove it with docker rm -f followed by the name shown in its NAMES column.

The red error lines never go away, and after 15 minutes the script stops. cilium status --wait gives up when its 15 minutes run out, and it may end with a long crash dump that starts like this, followed by many lines of goroutine details:

That dump only means the waiting ran out of time. Nothing is broken yet. Find out what the Cilium pods are doing.

-n kube-system looks in the namespace kube-system. A namespace is a named group that keeps Kubernetes objects apart, and Kubernetes and Cilium keep their own pods in this one. Look at the STATUS column of the pods whose names start with cilium-.

If it shows ContainerCreating, PodInitializing or a value starting with Init:, Cilium's images are still downloading, which takes longer on a slow connection. Don't delete the cluster, because that throws the finished downloads away. Run cilium status --wait until the four top lines end in OK, then run the rest of setup.sh by hand with this block.

If the STATUS column shows ImagePullBackOff or ErrImagePull, the nodes can't download Cilium's images at all. Check that Windows is online and that no VPN is running. Once the downloads work again, the status changes by itself, and you continue as in the previous paragraph.

If it shows CrashLoopBackOff, the pods start and crash over and over. Read the end of the log from the copy that crashed.

ds/cilium means the DaemonSet named cilium, and kubectl picks one of its pods. --previous reads the log of the container that crashed, not the fresh one that restarted a moment ago and may have written nothing yet. --tail 20 keeps the last 20 lines. If kubectl answers that there's no previous container, run the same command without --previous. If the lines mention TPROXY, xt_socket or iptables, a kernel module is missing. Go back to chapter 3, check the loadKernelModules line and the lsmod output, and run wsl --shutdown from PowerShell after fixing the file. Then reopen Ubuntu, run kind delete cluster and bash setup.sh again.

Errors that say Read-only file system or Input/output error, even for simple commands such as ls:

Drive C: is full. Ubuntu's virtual disk could not grow, so Linux switched its disk to read-only to protect your files, and nothing can be written until you restart it. Check it with mount | grep " / ". If the line contains emergency_ro, this is the cause. On Windows, free at least 15 GB on C: as in chapter 3's free-space step. Then run wsl --shutdown in PowerShell, open Ubuntu again, and check that mount | grep " / " no longer shows emergency_ro. Finish with cd ~/microseg, kind delete cluster and bash setup.sh.

An error from docker pull that contains this word:

Docker Hub limits how many images one internet address may download without an account, and a university network shares one address among many people. The cluster already exists and Cilium is running, so don't delete anything. Wait an hour or connect the laptop to a phone hotspot, then run the block from the previous failure, which repeats the rest of setup.sh from docker pull onward.

Check the nodes and their tier labels (kubectl get nodes)

Each node's tier label decides which pods it runs in chapter 6, so check both the state and the label of every node.

kubectl get nodes lists the nodes. -L tier adds a column showing each node's tier label.

You should see three nodes, all Ready.

The TIER column must be empty for kind-control-plane, frontend for kind-worker and backend for kind-worker2. VERSION must read v1.36.4 on all three.

If you see this instead

kubectl has no cluster to talk to, because kind create cluster never finished. Scroll up through the setup.sh output to its first ERROR line and use the failures listed in the previous step.

One or more nodes show NotReady. Cilium hasn't started on that node yet. Wait two minutes and run the command again. If it stays NotReady, follow the CrashLoopBackOff failure in the previous step.

The TIER column is empty for the workers too. The cluster was created from a kind-config.yaml without the labels: lines, usually because the file wasn't saved before setup.sh ran, or because the indentation is wrong and kind read the labels as part of something else. Compare the file with the one above, save it, then run kind delete cluster and bash setup.sh.

Check Cilium's health and the cluster DNS address

cilium status gives a one-screen report on every part of Cilium. Read it now, while the cluster is healthy, so you have a known-good report to compare against when something breaks later.

You should see a status block followed by a table of Cilium's parts.

In the block at the top, the lines for Cilium, Operator, Envoy DaemonSet and Hubble Relay must each end in OK, and disabled on the ClusterMesh line is expected. In the five rows that start with DaemonSet or Deployment, the count after Ready: must be full, such as 3/3, and its numbers must match the number after Desired:. A Deployment, the kind of object in the cilium-operator and hubble-relay rows, keeps a set number of copies of a pod running. Helm chart version: must read 1.20.5. The long sha256: codes after the image names are fingerprints of the exact images and may differ.

If you see this instead

Helm chart version: reads 1.20.3. Cilium was installed without --version 1.20.5, usually because that part of setup.sh was changed. Compare the file with the one in this chapter, save it, then run kind delete cluster and bash setup.sh.

One of the four top lines still shows errors. Wait two minutes and run cilium status again. If the errors stay, follow the CrashLoopBackOff failure in the setup.sh step.

Next, read the address of the cluster's DNS service, the service that turns names such as db, your database Service from chapter 6, into addresses. The nginx settings you write in chapter 5 contain this address.

get svc kube-dns shows the Service named kube-dns.

You should see one row for kube-dns.

CLUSTER-IP must read 10.96.0.10. kind always gives the DNS service this address, so if yours differs, your kind-config.yaml has extra lines. Compare it with the file above and rebuild with kind delete cluster and bash setup.sh.

Connect the hubble command to Hubble Relay (port 4245)

Hubble Relay runs inside the cluster, and the hubble command in Ubuntu can't reach it on its own. A port-forward fixes that. It's a tunnel that kubectl or the cilium command opens through the Kubernetes control plane, from a port on your laptop to a port inside the cluster.

cilium hubble port-forward opens the tunnel to Hubble Relay on port 4245 of your laptop, where the hubble command looks by default. The & at the end runs it in the background, so it keeps running while you type other commands. sleep 5 waits five seconds for the tunnel to open, and hubble status asks Hubble Relay for its state.

You should see Hubble's report on its own state.

A line such as [1] 2817 may come first. That's bash telling you the job number and process number it gave the background command, and yours will differ. In Hubble's report, the line that must match is Connected Nodes: 3/3, which means Relay is collecting records from all three nodes. The Current/Max Flows count fills up to its maximum within minutes and then stays there, and Flows/s changes all the time. The port-forward may also print a line of its own, now or later. If the prompt seems to disappear after that, press Enter to get it back.

A background command belongs to the terminal that started it. When you close this terminal, the port-forward stops, and you run the same cilium hubble port-forward & line again in the next session that needs Hubble. This tunnel is only for reading Hubble's records. Never use a port-forward for the attack in chapter 8, because its traffic skips the point where Cilium checks policy and the attack would always succeed.

If you see this instead

A long error from hubble status that ends in this text:

The tunnel wasn't open yet, or it failed to start. Run jobs, which lists this terminal's background commands. If the port-forward isn't listed as Running, start it again with cilium hubble port-forward &, wait a few seconds and run hubble status again.

An error from the port-forward containing this text:

A port-forward is already running, probably in another terminal window. That's fine, since one is enough. Run hubble status and check for Connected Nodes: 3/3.

Run Cilium's connectivity test

The connectivity test is Cilium's own test suite. It deploys test pods into three namespaces of its own, cilium-test-1, cilium-test-ccnp1 and cilium-test-ccnp2, and then works through a list of 138 tests: pods reaching pods on the same node and on the other node, pods reaching Services, DNS, network policies that must allow or block traffic, HTTP rules enforced by Envoy, and pods reaching the internet. About 83 of them run on this setup, and the rest are skipped because they don't apply. If it passes on your laptop, the Cilium features this guide relies on work here too. You also save its output, because chapter 14 uses it as evidence in your thesis.

(1) mkdir -p ~/microseg/evidence creates the folder where you keep outputs for your thesis.

(2) cilium connectivity test runs the whole suite and prints every test as it goes. Normally it also compares each connection with Hubble's records of it. On this setup Cilium sums those records up to save work, so the comparison can't find every record it expects and fails tests whose connections worked. --flow-validation=disabled switches that comparison off. Each test still passes or fails on whether its connections succeeded or were blocked as the test expects. 2>&1 sends error messages into the same stream as normal output, and tee shows everything on the screen and also saves it in the file named after it.

(3) An exit code is a number every program leaves behind when it finishes: 0 means success, anything else means failure. ${PIPESTATUS[0]} holds the exit code of the first command in the line before, here cilium connectivity test. The usual $? would give you the exit code of tee, which is 0 even when the test failed. tee -a adds the line to the end of the file instead of replacing the file.

The test runs its tests one after another, and each one prints a line ending in a counter such as [42/138], so you can see how far it has got. It can take up to an hour. Leave the terminal open and let it run to the end.

You should see the summary of the run, then the exit code.

The last line must read exit code 0, and the summary above it must say the tests were successful, with no failed test named. The numbers of tests that ran and were skipped can differ from the ones shown.

Lines on the way saying a test is skipped, such as Skipping test ... requires Cilium version >=1.21.0 or (skipped by condition), are normal. They mean the test doesn't apply to this setup. A line that starts with ❌ is a real failure. A run with failures ends with a summary that counts the failed tests and lists each one by name below that count, and the exit code is a number other than 0.

If you see this instead

The output stays on a line like this one for more than 5 minutes.

The test pods can't start, usually because their images can't download. Open a second Ubuntu window and run kubectl -n cilium-test-1 get pods. ImagePullBackOff or ErrImagePull in the STATUS column means the downloads fail. Fix the connection or switch to a phone hotspot, press Ctrl+C in the first window, delete the test namespaces with the command in the next step and run the test again.

The summary lists failed tests, and every one of them is a test that reaches outside the cluster. Their names contain to-fqdns, pod-to-world or pod-to-cidr, or they target 1.1.1.1 or one.one.one.one. Your network blocks those addresses, which is common on university and office networks. Cilium is fine, and nothing in this project needs the internet from inside the cluster. To get a clean result for your records, connect the laptop to a phone hotspot, delete the test namespaces as in the next step and run the test again.

One or two tests fail and they aren't internet tests. Delete the test namespaces and run the test once more. If the same tests fail again and cilium status still shows the four top lines ending in OK, write the names of those tests in your progress tracker and go on. Chapter 10 tests the features this project depends on directly.

Many different tests fail, including tests between pods. Something in Cilium isn't healthy. Run cilium status, fix what it reports using the steps earlier in this chapter, delete the test namespaces and run the test again. If it still fails after that, switch to appendix A, which builds the same lab in an Ubuntu virtual machine instead of WSL. Do it the same evening, while the rest of the schedule can still absorb it.

The test stopped halfway because the terminal closed or you pressed Ctrl+C. Delete the test namespaces and start it again. It always starts from the beginning.

Clean up after the test (kubectl delete ns)

The test leaves its namespaces behind. Delete them so they don't use memory for the rest of the project.

kubectl delete ns deletes the namespaces named after it, with everything inside them. --ignore-not-found stops kubectl from complaining about a name that doesn't exist.

You should see one line per deleted namespace. The command can take a minute, because Kubernetes stops every pod inside first.

If you see this instead

The prompt comes back with no output at all. The namespaces were already gone, which is fine, and --ignore-not-found kept kubectl quiet about it.

Open the Hubble UI (port 12000)

The Hubble UI is a web page that draws the connections Hubble records as a map, with every allowed and dropped flow listed under it. You'll use it in chapters 8 and 11 to show the attack moving through the network and then being stopped.

cilium hubble ui opens a port-forward from port 12000 on your laptop to the Hubble UI inside the cluster. It would also try to open a browser, but Ubuntu in WSL has none, so --open-browser=false switches that off and you open the page from Windows. & runs it in the background again. The curl line asks for the page and prints only the HTTP status code: -s hides progress, -o /dev/null throws the page itself away, and -w "%{http_code}\n" prints the code followed by a line break.

You should see a status code on the last line.

The last line must be 200, the HTTP code for "OK, here is the page". Any line before it, such as [2] 2954, comes from bash or from the cilium command starting in the background, and differs on every run.

Now open Edge or Chrome on Windows and go to http://localhost:12000. The Hubble page loads and asks you to choose a namespace. Choose kube-system. After a few seconds, boxes appear for the programs that talk to each other there, joined by lines, and the list of flows under the map fills up. Your own portal appears here from chapter 6 on, in the namespace campus.

If you see this instead

curl couldn't connect at all, because the UI's port-forward wasn't ready yet. Wait ten seconds and run the curl line again. If it still prints 000, run jobs, and if cilium hubble ui isn't listed as running, start it again.

The curl line prints 200 in Ubuntu, but the Windows browser says it can't reach localhost. Windows isn't receiving WSL's ports, so check that localhostForwarding=true is in your .wslconfig (chapter 3). WSL reads that file only when it starts, so after fixing it, run wsl --shutdown in PowerShell and reopen Ubuntu. The cluster comes back by itself, because its nodes are Docker containers that start again with Docker. Wait until kubectl get nodes shows all three nodes Ready, which can take two minutes, then open both tunnels again.

Open http://localhost:12000 in the Windows browser once more.

Checkpoint

Run these two commands. The first lists the nodes again, and the second prints the last line of the connectivity test you saved.

Three nodes must be Ready, with frontend in the TIER column for kind-worker and backend for kind-worker2. The last line must read exit code 0. A different exit code is only acceptable if the failed tests were the internet tests or the repeated one or two described in the connectivity test step. Write both results in your progress tracker. Don't start chapter 5 until both hold.

Save this state in Git.

The commit saves kind-config.yaml, setup.sh and the saved test output in evidence/. The images/ folder stays out of it, because .gitignore names it. Git answers with a line that contains main, a short commit code and your message, followed by 3 files changed.
