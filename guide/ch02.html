Chapter 2. Before you start

Nothing in the lab runs on plain Windows, so this chapter gets Ubuntu 24.04 running under WSL 2, with VS Code editing files inside it and Git keeping snapshots. By the end you'll have a project folder, ~/microseg, holding one small file you copied in from Windows, with your first Git snapshot saved and a backup copy on the Windows side. Plan on 1.5 to 2 hours, including one restart of Windows.

Step 1. Check that virtualization is on

WSL 2 runs Linux in a light virtual machine, and a virtual machine needs a feature of your processor called virtualization, which lets one computer behave like several. Many laptops ship with it switched off in the firmware, the small program that starts the computer before Windows does. Check it first, because an install that fails halfway rarely tells you why.

  1. Press Ctrl+Shift+Esc to open Task Manager.
  2. If the window is small and shows only a list of apps, click More details at the bottom.
  3. Click the Performance page in the left-hand column (its icon looks like a heart-rate line), then click CPU.
  4. Under the graph, find the line that starts with Virtualization:.

You should see Virtualization: Enabled. Close Task Manager. Go on to step 2.

If you see this instead

The line reads Virtualization: Disabled. The feature exists but is switched off in the firmware, and you have to switch it on there. Save your work and close every program, because the next steps restart the laptop. If your laptop uses BitLocker or device encryption, open aka.ms/myrecoverykey on your phone first and keep the recovery key at hand, because some laptops ask for it after a firmware change.

  1. Open Settings, then System, then Recovery.
  2. Next to "Advanced startup", click Restart now and confirm.
  3. On the blue screen that appears, choose Troubleshoot, then Advanced options, then UEFI Firmware Settings, then Restart. If there's no UEFI Firmware Settings tile, shut the laptop down, then press the power button and tap F2, Del or Esc (F10 on HP) until the firmware screen appears.
  4. The laptop restarts into its firmware settings, which look different on every brand. Look for a setting named Intel Virtualization Technology, Intel VT-x, SVM Mode or AMD-V, usually on a page called Advanced, CPU Configuration or Security.
  5. Set it to Enabled, then save and exit, usually with F10.

When Windows is back, check Task Manager once more, and carry on once it reads Enabled.

If you can't find the setting anywhere in the firmware, search the web for your exact laptop model followed by "enable virtualization BIOS". Some laptops hide the option until you press a key such as F7 for an advanced mode.

Step 2. Update WSL

The WSL that comes with Windows is usually too old for this lab, so update it first. The guide was tested with WSL 3.0.5.

WSL is managed from PowerShell running as administrator, the Windows account level that may change system settings. Press the Windows key, type powershell, right-click Windows PowerShell and choose Run as administrator. When Windows asks whether to allow the app to make changes, click Yes. The new window's title starts with Administrator:. Run the update.

wsl is the Windows program that manages WSL, and --update tells it to download and install the newest version. It prints a few lines about checking for and installing an update, and they depend on the version you started from, so they aren't reproduced here. The last line either names the version it installed or says the most recent version is already installed. Both are fine.

Now ask WSL which version it is.

--version prints the version of WSL and of the Linux kernel it runs.

You should see a short list of versions, like this one from the tested laptop.

The first line must read WSL version: 3.0.5.0 or a higher number, and the second line must read Kernel version: 6.18 followed by more digits, or a higher version. The other lines will differ on your laptop.

If you see this instead

If a long help text follows, the old WSL that came with Windows is still the one running. Run wsl --update again in the administrator window, restart Windows, then try wsl --version again.

If the update stops with an error code, or sits at 0% for more than ten minutes, your network is probably blocking the Microsoft Store, which WSL downloads through by default. Press Ctrl+C and run wsl --update --web-download, which fetches the same update from GitHub.

If the first line shows a version lower than 3.0.5.0, even though wsl --update said the newest version is already installed, run wsl --update --web-download in the administrator window, restart Windows and check again.

Step 3. Install Ubuntu 24.04 and create your Linux user

WSL can hold several Linux systems side by side, and each one is called a distribution, or distro. Ubuntu is one distribution, and it comes in several releases. You install the exact release the guide was tested with, Ubuntu 24.04, under the name Ubuntu-24.04. During the install Ubuntu asks you to create a Linux user, the account you'll work as inside Ubuntu. It's separate from your Windows account.

Pick the user name before you start. It must be lowercase letters and digits only, start with a letter and contain no spaces, for example sara. Then pick a password you'll remember. You'll type it often, because Ubuntu asks for it whenever you run a command with sudo, which runs that one command with administrator rights. Every time this guide writes <user>, it means this Linux user name.

In the same administrator PowerShell window, run the install.

--install installs WSL's parts if they're missing and then a distribution, and -d Ubuntu-24.04 names the distribution to install. The download is several hundred megabytes. Give it a few minutes.

When it asks for a user name, type the one you picked and press Enter. When it asks for a new password, type it and press Enter, then type it again when asked to retype it. Nothing appears on the screen while you type the password, not even dots. That's normal on Linux. Your typing goes in all the same, so type it blind and press Enter.

You should see the install progress, then the questions for the user name and the password, and at the end the Ubuntu prompt.

The last line is the Ubuntu prompt. It starts with your Linux user name, then @ and your computer's name, and it ends in $. Your names will differ from the tested laptop's.

On laptops where WSL had never been installed, the install may instead end with this message, because Windows has to switch on its virtual machine feature first.

Restart Windows. If an Ubuntu window opens on its own after the restart and asks for a user name, answer it there. Otherwise open PowerShell as administrator again and run wsl --install -d Ubuntu-24.04 a second time, and this time it installs Ubuntu and asks for the user name.

When the Ubuntu prompt appears, type exit and press Enter to return to PowerShell, then close the administrator window. You won't need administrator rights again in this chapter.

If you see this instead

Depending on the WSL version, the message also carries an error code containing 0x80370102 or HCS_E_HYPERV_NOT_INSTALLED. Windows can't start the virtual machine, either because virtualization is off in the firmware or because the Virtual Machine Platform part of Windows is missing. Check Task Manager again as in step 1. If it says Enabled, run wsl --install --no-distribution in an administrator PowerShell, restart Windows and run wsl --install -d Ubuntu-24.04 again.

The two passwords you typed weren't identical, which is a common slip when you can't see them. Type y, press Enter and type the password twice again, slowly.

Ubuntu 24.04 is already on this laptop from an earlier attempt. Older WSL releases say the same thing differently, that the distribution is already installed. If you remember that user's password, keep it and go on to step 4. If you've forgotten the user name too, run wsl -d Ubuntu-24.04 -u root ls /home in PowerShell, and the folder it prints is the name. To set a new password, run wsl -d Ubuntu-24.04 -u root passwd <user> with that name in place of <user>. The error The '<' operator is reserved for future use. means you left <user> in. To start completely fresh instead, run wsl --unregister Ubuntu-24.04, which deletes that Ubuntu and every file inside it, and then install again.

Step 4. Open the Ubuntu terminal

From now on you open Ubuntu in its own terminal window. Press the Windows key, type ubuntu and click the result with 24.04 in its name. If no such result shows up, open an ordinary PowerShell window and run wsl -d Ubuntu-24.04 --cd ~ instead, which starts the same Ubuntu in your Linux home folder. Leave this Ubuntu window open until step 6 tells you to close it.

Check which release you're in and whether Git, the snapshot program, is already installed.

/etc/os-release is the file where Ubuntu describes itself, and grep PRETTY_NAME prints only its line holding the release name. git --version prints Git's version, if Git is there.

You should see two lines.

The first must name Ubuntu 24.04. The guide was tested with 24.04.5 LTS. The second starts with git version 2., and any version 2 works.

If you see this instead

Your Ubuntu came without Git. Install it with apt, Ubuntu's package manager, which downloads and installs programs from Ubuntu's own servers. Run sudo apt update && sudo apt install -y git and type your Linux password when Ubuntu shows [sudo] password for <user>:. Nothing appears while you type. Then run git --version again.

If the first line names a different release, such as 22.04, this window belongs to another distribution. Close it, and open the one with 24.04 in its name or use the wsl -d Ubuntu-24.04 --cd ~ command above.

Step 5. Check that Ubuntu runs under WSL 2

WSL can run a distribution in two ways. Version 1 translates Linux requests into Windows ones and has no real Linux kernel, so Docker and Cilium can't run on it. Version 2 runs the real kernel. The lab needs version 2.

With the Ubuntu window still open, open an ordinary PowerShell window, not as administrator, and list the distributions.

-l lists the installed distributions and -v adds each one's state and WSL version.

You should see a small table.

The row for Ubuntu-24.04 must read Running in the STATE column and 2 in the VERSION column. It should also have a * in front of it, which marks the distribution WSL opens when you don't name one. Other rows may appear if you installed other distributions or Docker Desktop before. Leave them alone and look only at the Ubuntu-24.04 row.

If you see this instead

If the VERSION column shows 1 for Ubuntu-24.04, convert it with wsl --set-version Ubuntu-24.04 2, which takes a few minutes, then list again.

If the * sits in front of a different distribution, run wsl --set-default Ubuntu-24.04 and list again.

If the STATE column shows Stopped, you closed the Ubuntu window, and WSL stops a distribution soon after its last window closes. Open Ubuntu again as in step 4 and run wsl -l -v once more.

Step 6. Install VS Code and open your project folder in it

You'll write and paste every project file in VS Code (Visual Studio Code), a free code editor from Microsoft. VS Code runs on Windows, but its WSL extension lets it open folders that live inside Ubuntu and save files there directly, with Linux line endings. An extension is an add-on that gives VS Code a new ability.

  1. In your Windows browser, open https://code.visualstudio.com and click the download button for Windows.
  2. Run the installer and accept the defaults. On the page called "Select Additional Tasks", check that Add to PATH is ticked, because that's what lets you start VS Code from the Ubuntu terminal.
  3. When the install finishes, open VS Code.
  4. Press Ctrl+Shift+X to open the Extensions view, type WSL in its search box, and on the extension named WSL published by Microsoft click Install.
  5. Close VS Code.

Ubuntu learns where the Windows programs are when its terminal starts, and your Ubuntu window started before VS Code existed. Close every terminal window you have open, Ubuntu and PowerShell both. Then open Ubuntu again from the Start menu.

Everything you build lives in one folder, ~/microseg, inside your Linux home folder. In the Ubuntu terminal, create it, move into it, print where you are and open it in VS Code.

mkdir -p ~/microseg creates the folder, and -p keeps it quiet if the folder already exists. cd ~/microseg moves you into it, so the commands after it work inside that folder. pwd prints the full path of the folder you're in. code starts VS Code, and . means "the folder I'm in". The first time you run code, VS Code installs a small helper program inside Ubuntu, the VS Code Server, which lets the Windows window work on Linux files.

You should see the folder's path, then a few lines about the VS Code Server being installed the first time.

The first line must read /home/<user>/microseg with your own Linux user name in it. The output may end with a line that contains ERROR:third_party\crashpad and CreateFile: The system cannot find the file specified. (0x2). That line comes from VS Code's crash reporter on Windows and is harmless, so ignore it. On later runs code . prints nothing. The prompt now ends in ~/microseg$, which also tells you where you are.

A VS Code window opens. Its title bar ends with [WSL: Ubuntu-24.04], and the bottom-left corner shows WSL: Ubuntu-24.04 on a coloured patch. If VS Code asks "Do you trust the authors of the files in this folder?", click Yes, I trust the authors, since you're the author. The Explorer pane on the left shows the folder MICROSEG, still empty.

If you see this instead

The shorter code: command not found means the same thing. Don't run the snap command it suggests, which would install a second, Linux copy of VS Code. Ubuntu doesn't know about your Windows VS Code yet. Close every terminal window, Ubuntu and PowerShell both, open Ubuntu again and run cd ~/microseg and then code . again. If it still fails, run the VS Code installer again and check that Add to PATH is ticked.

If VS Code opens but the title bar doesn't show [WSL: Ubuntu-24.04] and the bottom-left corner has no WSL patch, the WSL extension is missing. VS Code then opens the folder from the Windows side, which writes Windows line endings. Close that window, install the WSL extension as in item 4 above, then run code . again from the Ubuntu terminal.

Step 7. Move a file from Windows into Ubuntu

Sooner or later you'll have a file on Windows that belongs in the project, from a download or an email. Windows drive C: appears inside Ubuntu as the folder /mnt/c. That's a mount, a place where one file system shows up inside another. Your Windows Downloads folder is therefore /mnt/c/Users/<WinUser>/Downloads in Ubuntu, where <WinUser> is the name of your Windows user folder.

That name isn't always your display name. Windows sometimes shortens it, for example to the first five letters of your email address. List the user folders to find yours.

ls lists the contents of a folder. It prints the folder names on one or more lines.

You should see a handful of names, yours among them.

Names such as Public, Default, 'Default User', 'All Users', defaultuser0 and the file desktop.ini belong to Windows itself, and some laptops also show accounts made by other programs, such as WsiAccount. ls puts names that contain spaces in quotes. Your own name, ASUS on the tested laptop, should match the <WinUser> you found in chapter 0. Write it down. Chapter 3 and later chapters use it again.

Now the drill. On Windows, open Notepad, type the line copied from Windows and press Enter once, so the line ends with a line break. Choose File, then Save as, click Downloads in the left-hand pane and type hello.txt as the file name. Leave "Save as type" on "Text documents (*.txt)" and click Save.

Back in the Ubuntu terminal, copy the file into your project folder and print it. Replace <WinUser> with your Windows user folder name. Editing in the middle of a long line in the terminal is awkward, so paste the block into Notepad first, replace every <WinUser> there, then copy it from Notepad into the Ubuntu terminal.

cp copies the file given first into the folder given second. cat prints a file's contents.

You should see your line on its own.

The output must read exactly copied from Windows, with the prompt on the next line. hello.txt also appears in VS Code's Explorer pane.

You can look at your project folder from the Windows side too. Run explorer.exe . in the Ubuntu terminal while you're in ~/microseg. Ubuntu can start File Explorer because WSL lets it run Windows programs, and the . again means the folder you're in. A File Explorer window opens on the folder, showing hello.txt. You can reach the same place from any File Explorer address bar by typing \\wsl.localhost\Ubuntu-24.04\home\<user>\microseg, and File Explorer also lists Ubuntu under Linux in its left-hand pane.

Use that window to look, and change files with VS Code or the Ubuntu terminal. Windows can open files inside Ubuntu and Ubuntu can open files on drive C:, but the project stays in ~/microseg and never moves under /mnt/c. If you ever drag a downloaded file into the Ubuntu folder through File Explorer, a second file with the same name plus :Zone.Identifier appears next to it, a note Windows attaches to say where the download came from. It's harmless clutter. Delete such files with rm ~/microseg/*:Zone.Identifier, and copy files in with cp from the Ubuntu terminal instead.

If you see this instead

The first line may start with bash: without the dash. You pasted the line without replacing <WinUser>. Bash reads < and > as special characters, so the cp command never ran and nothing was copied. Paste the block into Notepad, replace <WinUser> with your folder name and no angle brackets, and paste it into the terminal again.

Your message shows your own folder name where this one shows sarak, and the path names a file that doesn't exist. Compare the name's spelling with the ls /mnt/c/Users/ output, then run ls /mnt/c/Users/<WinUser>/Downloads/ with your name in place to see what the file is really called. A name like hello.txt.txt means Windows added a second .txt behind your back. In File Explorer, choose View, then Show, then File name extensions so you can see full names. Rename the file to hello.txt and copy it again.

If the output reads copied from Windows with the prompt glued onto the end of the same line, you didn't press Enter after the text in Notepad, so the file has no line break at the end. Open it in Notepad, click at the end of the line, press Enter, save, and run the two commands again.

Step 8. Line endings and safe pasting

A line ending is the invisible character, or pair of characters, that marks where a line of text ends. Linux uses one character, called LF (line feed). Windows uses two, CR (carriage return) followed by LF, which together are called CRLF. You rarely see the difference. Bash does, though, because it reads the CR as part of the command, so a script saved with CRLF fails with errors that make no sense at first sight. A YAML file can break the same way. YAML is the text format Kubernetes files are written in, where indentation shows which line belongs to which. Your hello.txt came from Notepad, so it has a Windows line ending. Show it, remove it and show it again.

-A makes cat print invisible characters as visible codes. A CR shows as ^M and the end of each line shows as $. sed edits text, and -i makes it change the file in place. Its expression s/\r$// means "replace a carriage return at the end of a line with nothing". You'll use the same sed command in chapter 13 on any script that picked up Windows line endings.

You should see the same line twice, with different endings.

The first line must end in ^M$, where ^M is the Windows carriage return. The second must end in $ alone. The file is now Linux-style.

Files you create in the VS Code window that shows [WSL: Ubuntu-24.04] get LF line endings from the start. Set VS Code up so you can confirm that at a glance and so stray tabs show up too. Indentation is the spaces at the start of a line, and YAML and Python both read meaning from it. A tab can look exactly like a few spaces on screen, yet YAML refuses tabs for indentation and Python fails when tabs and spaces are mixed.

  1. In VS Code, press Ctrl+, to open Settings.
  2. Type render whitespace in the search box at the top, and set Editor: Render Whitespace to all. Spaces now show as faint dots and tabs as small arrows.
  3. Type eol in the search box and set Files: Eol to \n, which is LF.
  4. Close the Settings tab and click hello.txt in the Explorer pane to open it.

The status bar along the bottom of the VS Code window now shows Spaces: 4, UTF-8 and LF toward the right. If it shows CRLF, click it and choose LF from the list at the top of the window. If it shows Tab Size: instead of Spaces:, click it and choose Indent Using Spaces. Look at the LF and Spaces: items every time you paste a file in later chapters.

A paste can go wrong in VS Code and in the terminal, in different ways. To paste a whole file into VS Code, create the file first, click into the empty file so the cursor sits at line 1, column 1, and press Ctrl+V. Then compare the first and the last line with the guide. A paste that went wrong usually shows at one of the ends.

In the Ubuntu terminal you paste with Ctrl+Shift+V or with a right-click. When you paste several lines at once, the terminal may warn that the text contains multiple lines, and you click Paste anyway when the text came from this guide. Paste one block at a time. Wait for the prompt to come back before you paste the next. If the pasted lines sit highlighted on the command line and nothing runs, press Enter.

If you see this instead

The prompt has turned into a bare > and nothing you type does anything useful. The terminal is waiting for you to close a quote or a block that the paste didn't finish, usually because a quote mark was lost or turned curly in copying. Press Ctrl+C to cancel, copy the block again from the Docs page and paste it again.

This message, often with a script name and line number in front of it, means you ran a script that has Windows line endings. Run sed -i 's/\r$//' followed by the script's path, as above, then run the script again.

Step 9. Set up Git and create the repository

Git keeps snapshots of your project folder. It shows you exactly what you changed since the last snapshot, and it takes you back to a state that worked. It first needs to know who you are, because it writes your name and email into every snapshot. Replace the two placeholders with your own name and email, and keep the double quotes.

git config --global saves a setting for every project of this Linux user. user.name and user.email are the name and email written into your snapshots, and since your thesis appendix will show this history, use your real name. init.defaultBranch main names the main line of snapshots main in every new project. --list prints the settings you saved.

You should see the three settings, one per line.

The lines must show your name and email after user.name= and user.email=. Git prints the third setting in lower case, as init.defaultbranch=main. That's normal.

If you see this instead

You left a placeholder in. The double quotes kept bash from treating the angle brackets as special, so Git stored the placeholder as your name. Run the user.name line again with your real name between the quotes, and do the same for user.email if it shows <your-email>. The new value replaces the old one.

A repository is a folder that Git tracks, together with the history of its snapshots, which Git keeps in a hidden folder called .git. Some folders that appear later must stay out of the snapshots, because they're large or because a script rebuilds them. A file named .gitignore lists them, and Git skips anything that matches a line in it. Turn ~/microseg into a repository and create that file. Paste the block as one piece, and if the terminal warns about multiple lines, click Paste anyway.

git init creates the hidden .git folder in the folder you're in. cat > ~/microseg/.gitignore writes into that file whatever cat receives, and <<'EOF' feeds it every line that follows, up to the line that holds only EOF. These are the folders to skip.

  • .venv/ is the Python setup you create in chapter 3. One command rebuilds it.
  • __pycache__/ holds files that Python creates on its own when it runs your code.
  • images/ holds image archives of hundreds of megabytes, which setup.sh and deploy.sh rebuild.
  • results/ holds the measurements measure.py writes in chapter 12, and your backup keeps those.

The last command prints the file so you can check it.

You should see one line from Git and then the four folder names.

The first line must start with Initialized empty Git repository in and end with /home/<user>/microseg/.git/, with your Linux user name. Exactly four lines follow, .venv/, __pycache__/, images/ and results/, with nothing else.

If you see this instead

That line and several more hint: lines appear after git init when the init.defaultBranch setting is missing. Run git branch -m main to rename the branch, then check that git status starts with On branch main.

Step 10. Save the first snapshot

First ask Git what it sees.

git status reports which files are new, changed or ready to be saved in the next snapshot. Run it whenever you're unsure what state your folder is in.

You should see the branch name and the two files.

The first line must read On branch main. Under Untracked files: the output lists .gitignore and hello.txt, which means Git sees them but doesn't track them yet.

A snapshot in Git is called a commit, and making one takes two moves. Staging picks the changes that go into the next commit. Committing saves them, with a message that says what changed. This commit is also the one for this chapter. Commit, then list the commits.

git add -A stages every new, changed and deleted file in the repository, apart from what .gitignore excludes. && runs the second command only if the first succeeded. git commit -m saves the staged changes as a commit, with the text in quotes as its message. git log lists commits, newest first, and --oneline shrinks each one to a single line.

You should see a short summary of the commit, then one line of history.

The summary's first line starts with [main (root-commit), followed by a short code and your message. "root-commit" means it's the first commit in the repository. A later line says 2 files changed. The last line, from git log, starts with a seven-character code that's different on your laptop, followed by your message. Git may also print (HEAD -> main) before the message, which marks the newest commit on the branch main. That seven-character code goes into the Commit column of your progress tracker from chapter 0.

If you see this instead

You ran a Git command outside the repository, probably in a fresh terminal that starts in your home folder. Run cd ~/microseg and try again.

The message goes on to suggest git config commands and ends with a line starting fatal: unable to auto-detect email address. Git doesn't know your name and email, because the settings in step 9 didn't take effect. Run the four git config commands from step 9 again, then run the commit again.

Git found nothing new to save, which means the commit already exists. Run git log --oneline to see it.

Step 11. See a change and undo it

Two more Git commands get you out of most trouble later. git diff shows what changed in your files since the last commit, and git restore throws those changes away. Practise both on hello.txt now, while nothing depends on it. The block moves into the project folder, adds a line to the file, shows the difference, undoes it and prints the file.

cd ~/microseg makes sure Git runs inside the repository. echo prints its text, and >> adds that text to the end of the file instead of printing it. git diff compares your files with the last commit. git restore hello.txt puts the file back the way it was in the last commit, and cat shows the result.

You should see the difference first, then the original line on its own.

In the git diff part, the line that counts is +a line to throw away. A + at the start marks a line you added, a - would mark a line you removed, and lines with neither are unchanged context. The very last line must read copied from Windows, with nothing after it. When a file you pasted goes wrong in a later chapter, git diff shows exactly what changed since it last worked, and git restore with the file's name brings the working version back.

A pager is a program that shows long output one screen at a time. When git diff or git log has more to show than fits in the window, Git hands the output to a pager, the last line of the window reads : or (END), and the prompt doesn't come back. Use the arrow keys to scroll and press q to get the prompt back.

If you see this instead

git diff printed nothing before this line, because hello.txt isn't in any commit yet. The commit in step 10 didn't go through. Your extra line is still in the file, so remove it with sed -i '$d' ~/microseg/hello.txt, where $d means "delete the last line". Then go back to step 10, make the commit and run this block again.

Step 12. Back up the project to Windows

Git keeps its snapshots inside ~/microseg/.git, so if Ubuntu breaks or gets deleted, the snapshots go with it. A copy on Windows guards against that. An archive is one file that holds many files and folders, and tar is the Linux program that makes archives. Make your first backup now with the block below. Replace <WinUser> in all three lines, the same way as in step 7, by pasting the block into Notepad first, replacing every <WinUser> there and copying it from Notepad into the Ubuntu terminal.

Take the first line piece by piece.

  • The two --exclude options leave out .venv and images, which are large and can be rebuilt.
  • -c creates an archive, -z compresses it and -f names the file to write.
  • $(date +%F) puts today's date into the file name, such as 2026-11-20, so each backup gets its own name.
  • -C ~ microseg means "go to my home folder and archive the folder microseg from there", so the paths inside the archive start at microseg/.

The archive includes .git, so the backup carries your whole history. ls -lh lists your backups with their sizes in a readable form. tar -tzf lists what's inside an archive without unpacking it. Today there's only one backup, so the * matches exactly one file.

You should see one line from ls for today's backup, and then a list of paths.

The ls line ends with microseg-backup-, today's date and .tar.gz. The size is a few kilobytes for now, and it grows as the project fills up. Every path in the list after it starts with microseg/, and the list must include microseg/hello.txt, microseg/.gitignore and many entries under microseg/.git/.

Back up again once a week, and each time you finish chapter 6, 10 or 12. From your second backup on, use the two-line block below instead. It leaves out the tar -tzf line, which fails once the * matches more than one archive. Don't run it today.

The ls line then lists one archive per backup, newest date last.

To restore a backup later, you would run tar -xzf with the archive's path and -C ~. It unpacks the archive back into your home folder and overwrites the files there. Don't run it now.
