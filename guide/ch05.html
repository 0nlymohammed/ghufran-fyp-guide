Chapter 5. Write the services

By the end of this chapter your ~/microseg folder holds the ten files that make up the Campus Portal. Four are Python programs and one fills the database. Two belong to the web server, and the last three describe how to build your images. You'll build both of your own images, campus-app:1.0 and campus-news:1.0, and then fire the news bug at a throwaway container on your laptop and watch it answer as uid=1000(app). Nothing goes into the cluster until chapter 6.

Plan on 6 to 8 hours in two sittings. The first sitting covers the database file, auth and api. The second covers news, admin, the two frontend files, the image recipes and the tests. You paste most files and then check them, but one function, check_image in apps/news.py, you type by hand.

Figure 3 shows the services you're about to write and how a request from your browser reaches them. Notice that everything enters through one door, port 30080 on frontend, and that frontend talks only to api and news.

The database's tables and starting data, db/init.sql

The database starts out empty. The PostgreSQL image runs this file once, the first time its container starts with no data, and the file creates the three tables and fills them with four students and their grades. Every grade Omar tries to change in chapter 8 lives in a table this file creates.

The file is written in SQL (Structured Query Language), the language used to create tables in a database and to ask it questions. A table is like a spreadsheet. Its columns have names and types, and each row holds one record.

Create db/init.sql and paste this.

(1) Lines 1 to 9 create the table students. Each line inside the brackets is one column, its name first and its type after. SERIAL is a whole number that PostgreSQL fills in by itself, 1 for the first row, 2 for the second and so on. PRIMARY KEY marks the column that identifies a row, so no two rows can share an id. TEXT holds text of any length and INT holds a whole number. UNIQUE refuses a second student with the same user name, and NOT NULL refuses any row that leaves that column empty.

(2) Line 8, password_hash. The table never holds a password. It holds a hash, a one-way fingerprint of the password. Hashing the same password always gives the same hash, but nobody can turn a hash back into the password, so auth.py checks a login by hashing what was typed and comparing the two hashes.

(3) Lines 11 to 16 create grades. REFERENCES students(id) makes student_id a foreign key, a column whose value must be the id of a row that exists in another table. PostgreSQL refuses a grade for a student who doesn't exist.

(4) Lines 18 to 22 create sessions, one row per login. token is the random string a browser receives after a correct password. DEFAULT now() fills created_at with the current time.

(5) Lines 24 to 28 add the four students. INSERT INTO students (...) VALUES names the columns, then lists one bracketed row per student, with commas between the rows and ; after the last one, because every SQL statement ends with ;. The last value of each row, encode(sha256('sara2026'::bytea), 'hex'), computes the hash inside PostgreSQL. ::bytea turns the text into raw bytes, sha256(...) hashes them, and encode(..., 'hex') writes the result as 64 characters from 0 to 9 and a to f. That's the same format Python produces in auth.py, which is why logins work.

(6) Lines 30 to 38 add eight grades. Rows get their id in the order they go in. The third row, student 2 (omar), Network Security, 58, gets id 3. That's the row the attack in chapter 8 changes to 95.

The login service, apps/auth.py

auth is the only service that checks passwords and the only one that hands out tokens. api asks it about every request a logged-in student makes, so you write it first.

A few Python words before you paste. A module is one .py file, and import loads a module so your file can use what's in it. A function is a named block of code that runs when something calls it, and def starts one. Python groups lines by indentation, the spaces at the start of a line. Every line indented under a def belongs to that function, and this project uses four spaces per level. A string is a piece of text between quotes, such as "ok". Flask is a small library for writing web services. You write a function, put a route above it naming a path such as /login, and Flask calls the function whenever a request for that path arrives.

Create apps/auth.py and paste this.

(1) Line 1 is a comment. Python ignores everything after a #.

(2) Lines 2 to 8 load what the file needs. hashlib computes hashes, os reads environment variables and secrets makes random tokens. psycopg2 is the PostgreSQL driver, the library Python uses to talk to a PostgreSQL server. Flask and request come from Flask.

(3) Line 10, app = Flask(__name__), creates the web application. You'll need the name app again in chapter 6, where the command that starts this service asks for auth:app, the object called app inside auth.py.

(4) Lines 13 to 23 define query, a helper the routes call to talk to the database. params=() means the second argument is optional and defaults to an empty tuple, (), meaning no values. A tuple is Python's fixed list, written in round brackets. The text in triple quotes describes the function to human readers. psycopg2.connect(...) opens a connection to the host named db, and os.environ["POSTGRES_DB"] reads the environment variable POSTGRES_DB. In chapter 6 Kubernetes fills these variables from a Secret, so the password never appears in the code. connect_timeout=3 gives up after three seconds. RealDictCursor makes each row come back as a dictionary, Python's set of name: value pairs, so the code can write rows[0]["id"]. execute runs the statement, fetchall collects every row it returned, commit saves any change and close ends the connection. Opening a fresh connection for every statement is slow, but it keeps the code short. api and admin carry a copy of the same helper.

(5) Lines 26 to 28 are the simplest route. A line that starts with @ is a decorator, a label that changes the function below it. @app.get("/healthz") tells Flask to call healthz() whenever a GET request for /healthz arrives. The function returns ok, and Flask sends that back with status code 200, which means success. In chapter 6 Kubernetes calls /healthz every 10 seconds to find out whether the service is ready.

(6) Lines 31 to 34 start the login route, which takes POST requests. request.get_json() reads the body of the request as JSON (JavaScript Object Notation), the text format web services use for data, such as {"username": "omar", "password": "omar2026"}, and turns it into a dictionary. Line 34 hashes the typed password. .encode() turns the text into bytes, sha256 hashes them and hexdigest() writes the 64-character form that init.sql stored.

(7) Lines 35 and 36 ask the database for a student with that name and that hash. The SQL holds two %s markers, and the two values travel separately, in the brackets after the comma. psycopg2 hands them to PostgreSQL as data, never as part of the SQL text, so a user name such as ' OR '1'='1 can't change what the statement does. This is a parameterized query. It's why the portal has no SQL injection, the database cousin of the command injection in news.

(8) Lines 37 and 38 handle a wrong password. if not rows: is true when the database found nothing. When a Flask function returns a dictionary, Flask sends it as JSON, and a second value after the comma sets the status code. 401 means "you aren't logged in".

(9) Lines 39 to 41 handle a right password. secrets.token_hex(16) makes 16 random bytes and writes them as 32 characters. That's the token. Line 40 stores it with the student's id and line 41 sends it back. The RETURNING token at the end of the SQL is there because query always calls fetchall, and psycopg2 raises an error when you fetch rows from a statement that returns none.

(10) Lines 44 to 50 check a token for api. A header is a named line of extra information that travels with an HTTP request. The browser sends the token in the Authorization header as Bearer followed by a space and the token, and .replace("Bearer ", "") cuts that word off. request.headers.get("Authorization", "") gives an empty string when the header is missing, so a request without a token gets 401 instead of crashing the route.

Check the grammar with py_compile

py_compile is a tool that comes with Python. It reads a .py file and translates it the way Python would before running it, but it doesn't run anything. A missing bracket, a quote left open or a wrong indent shows up as an error. It can't tell you whether the logic is right, and it doesn't need Flask or psycopg2 installed, which is why it works with the plain python3 in Ubuntu.

python3 -m py_compile apps/auth.py checks the file and prints nothing when it's fine. Silence is hard to read, so && echo "auth.py compiles" prints a line, and only when the check passed. The check also leaves a folder called apps/__pycache__ behind, which Git ignores.

You should see one line.

If you see this instead

The last line of a Python error names the problem. A line further up gives the file name and the line number. Press Ctrl+G in VS Code and type the number to jump there.

A line starts with more spaces than its place allows. This usually comes from pasting into a line that already had spaces in it. Make the line start exactly where its neighbours start.

Some lines are indented with tab characters and others with spaces, and Python refuses to guess how they line up. Turn on Render Whitespace as you did in chapter 2. Tabs show as arrows and spaces as dots. Press Ctrl+Shift+P, type Convert Indentation to Spaces, press Enter and save.

The file isn't where the command expects it. It may have landed in the wrong folder or been saved under another name, such as Auth.py or auth.py.txt. Run ls apps to see what's really there and rename the file in VS Code by right-clicking it and choosing Rename.

The student API, apps/api.py

api is the back end the portal page talks to once a student has logged in. It never checks a password itself. It passes the login on to auth, and for every other request it asks auth who owns the token before it reads the database. It also carries a forgotten debug route, /api/export, which the L7 rule in chapter 10 shuts.

Create apps/api.py and paste this.

(1) Line 5 loads requests, a library that sends HTTP requests from Python the way a browser does. Line 6 adds jsonify from Flask.

(2) Line 10, AUTH_URL = "http://auth:5001". auth is the name of the auth Service you create in chapter 6 and 5001 is its port. Inside the cluster, DNS turns the name auth into the right address.

(3) Lines 13 to 23 repeat query.

(4) Lines 26 to 32 define current_student(). It sends the browser's Authorization header on to auth's /verify route and gives up if auth doesn't connect or answer within three seconds. If auth can't be reached at all, the request fails with an error page (status 500) instead. If auth answers with anything other than 200, the function returns None, Python's word for "nothing". Otherwise answer.json() reads auth's JSON answer and the function returns the student_id in it.

(5) Lines 40 to 43, /api/login. The JSON body from the browser goes to auth's /login unchanged, and auth's answer and status code go back to the browser unchanged. The browser's login request goes through nginx to api and never reaches auth directly, so auth stays out of its reach.

(6) Lines 46 to 52, /api/profile. Without a valid token the route returns 401. With one, it reads five columns of that student's row. (student_id,) with its trailing comma is a tuple holding exactly one value, and without the comma Python would read it as a plain number in brackets. jsonify(rows[0]) sends the first and only row as JSON.

(7) Lines 55 to 61, /api/grades, follow the same pattern and return all of this student's grades, sorted by course.

(8) Lines 64 to 68, /api/export, never call current_student(). Anyone who can reach this route gets every grade of every student, with no login at all. Frontend has to reach api for the portal to work, so the L3/L4 rules alone can't protect this route. In chapter 10 an L7 rule allows only three exact method and path pairs, and /api/export gets 403.

The news service, apps/news.py

news shows the announcements on the portal page and offers the image link checker for news editors. That checker is the attacker's way in. You type its function by hand, because typing makes you read every character.

Create apps/news.py and paste the whole file below. Then delete lines 26 to 34. Click in front of the @ at the start of line 26, hold Shift, click after the last character of line 34, and press Delete. Now type those nine lines back in yourself, reading them from the block, without copying. In the block they start at @app.post("/news/check-image") and run to the last line of the file, the one that starts with return.

Read these tips before you start typing. Each indent level is four spaces, and pressing Tab in a .py file in VS Code puts in four spaces for you. After a line that ends in :, VS Code indents the next line by itself, so don't add spaces on top of that. When VS Code adds a closing bracket or quote for you, type the closing character anyway when you reach it, and VS Code usually steps over its own instead of adding a second one. On line 31 the \\n has two backslashes, and there's a space between 3 and the closing ".

(1) Lines 1 and 2 are comments. They say the bug is deliberate.

(2) Line 3 loads subprocess, the module Python uses to start other programs.

(3) Lines 9 to 13 hold the three announcements as a list of dictionaries, written straight into the code. news has no database and nothing worth stealing. The attacker wants it for where it leads.

(4) Lines 21 to 23 send the list as JSON when a GET request for /news arrives. The portal page asks for it every time it loads.

(5) Line 26 answers POST requests for /news/check-image, which is where the checker form on the portal page sends its data.

(6) Line 28 reads the field called url from a submitted form. A form on a web page, like the checker form you add to index.html below, sends its fields as url=..., and the test at the end of this chapter sends the same thing with curl. If the field is missing, url becomes an empty string.

(7) Line 31 builds one line of text, a complete curl command. -s keeps curl quiet, -o /dev/null throws the downloaded picture away, -w '%{http_code}\\n' prints only the HTTP status code followed by a line break, and --max-time 3 gives up after three seconds. Then + url glues the user's text onto the end, with nothing checking what that text contains. Inside a Python string \\ stands for one backslash, so the command ends up holding \n, which curl turns into a line break.

(8) Lines 32 and 33 run that line. shell=True hands the whole line to a shell, /bin/sh, and the shell splits it at every ; and runs each piece as its own command. Together with line 31, this is what makes the injection possible. stdout=subprocess.PIPE collects what the commands print, stderr=subprocess.STDOUT adds their error messages to the same collection, text=True returns it as text instead of raw bytes, and timeout=20 makes Python kill the shell after 20 seconds. In that case the request fails with an error page instead of returning the output.

(9) Line 34 sends back HTTP status of image: followed by everything the shell printed, with status 200. Content-Type is a header that tells the browser what kind of answer this is, here plain text. Whatever the attacker's commands print comes back to the attacker in this reply.

The portal's web server, frontend/default.conf and frontend/index.html

frontend runs nginx, a web server, and it's the only service your browser ever talks to. It sends the portal page, and it passes every request for /api/ or /news on to the service behind it. A server that passes requests on like this is called a reverse proxy. You don't write a program for frontend. The stock nginx:1.28 image reads these two files, which chapter 6 hands to it.

Create frontend/default.conf and paste this.

(1) Line 2, server {, opens the settings for one website, and the } on line 26 closes them. Every setting inside ends with ;. listen 80 makes nginx accept connections on port 80. Port 30080 in Figure 3 is the NodePort, the door on the node, and in chapter 6 Kubernetes forwards it to this port 80 inside the frontend pod.

(2) Line 4, root, names the folder nginx sends files from. Chapter 6 puts index.html there, and a request for / gets that page.

(3) Line 8, resolver. nginx has to turn a name such as api.campus.svc.cluster.local into an address, and this line tells it which DNS server to ask, kube-dns at 10.96.0.10, the fixed address kind gives the cluster's DNS service. valid=10s makes nginx forget each answer after 10 seconds and ask again, so it finds a service that came back at a new address. ipv6=off makes it ask for IPv4 addresses only, the kind your cluster uses.

(4) Line 10, proxy_http_version 1.1. Toward the services behind it nginx speaks HTTP/1.0 unless told otherwise. Envoy, the proxy that checks the L7 rule in chapter 10, expects HTTP/1.1, so this line switches nginx to 1.1.

(5) Line 11, proxy_connect_timeout 5s. If a connection to a service can't open within 5 seconds, nginx gives up and returns an error page. Without this line it would wait a full minute. When a policy drops a connection, nothing ever answers, so the shorter wait makes a blocked flow show up fast.

(6) Lines 13 to 15. location = /healthz matches exactly that path, and nginx answers ok by itself. Kubernetes uses it the same way as the /healthz routes in the Python files.

(7) Lines 17 to 20 handle every request whose path starts with /api/. set $api ... stores the full address of api in a variable, and proxy_pass $api sends the request there with its path unchanged. nginx needs the variable here. When proxy_pass names a host directly, nginx looks that name up once when it starts and refuses to start at all if the name doesn't exist yet. With a variable it looks the name up at the moment a request arrives, through the resolver from line 8.

(8) Lines 22 to 25 do the same for news on port 5000. location /news covers both /news and /news/check-image.

Lines 6 and 7 explain why the addresses are written out in full. Inside a pod, the file /etc/resolv.conf holds a search list, a list of endings that programs try after a short name. That's how plain auth works in api.py. The search list turns it into auth.campus.svc.cluster.local before the lookup. nginx's own resolver skips the search list, so here the names have to be complete.

There is no location for auth, db or admin, so the browser can't ask nginx for any of them. On a flat network every pod can still reach them directly, though, and chapter 8 does exactly that.

Create frontend/index.html and paste this.

(1) HTML (HyperText Markup Language) is the language of web pages, made of tags in angle brackets such as <h1> for a big heading. Lines 1 to 6 are the page's header, and <title> sets the text on the browser tab.

(2) Lines 10 and 11 add a heading and an empty list, <ul id="news">. The id gives the list a name the script below can find it by.

(3) Lines 13 to 17 add two input boxes, a button and an empty <pre> area called result. onclick="login()" runs the login function when the button is clicked.

(4) Lines 19 to 23 are the image checker, a form. method="post" and action="/news/check-image" make the Check button send a POST request to that path, and name="url" makes the box's text travel as the field url. That's exactly the request the attack sends with curl in chapter 8.

(5) Lines 25 to 59 are JavaScript, the language browsers run inside a page. async and await let the page wait for an answer from the server without freezing. loadNews() asks nginx for /news, reads the JSON and adds one list item per announcement. It uses textContent, which puts the title in as plain text, so a title that contained HTML tags would show up as text instead of running as part of the page.

(6) login() sends the user name and password as JSON to /api/login. The Content-Type: application/json header tells api the body is JSON. If the answer holds no token, the page shows Login failed. Otherwise it builds the Authorization header from the word Bearer, a space and the token, asks for /api/profile and /api/grades, and prints both answers. JSON.stringify(..., null, 2) turns them back into JSON text with two-space indents so a person can read them.

(7) Line 58 calls loadNews() once when the page loads, which is why the announcements appear without a click.

Test default.conf with nginx -t

nginx can check a settings file without starting the server. Run that check in a throwaway nginx container with your file in place of the stock one.

-v puts your default.conf at the path where the nginx image keeps its own, read-only. nginx:1.28 is the image setup.sh downloaded in chapter 4. nginx -t is the command the container runs. -t means test the settings and stop. The image recipes, apps/Dockerfile and apps/Dockerfile.news

A Dockerfile is the recipe Docker follows to build an image, one instruction per line. Your project uses two. The first builds campus-app:1.0, which holds all four Python programs. The second builds campus-news:1.0 on top of it and adds the attacker's tools.

Create apps/Dockerfile and paste this. The name has no extension and starts with a capital D.

(1) Line 2, FROM python:3.12-slim, starts from the official Python 3.12 image in its slim form, a small Debian Linux with Python installed and little else.

(2) Line 3. RUN runs a command while the image is being built and keeps whatever it changes. apt-get update downloads Debian's current list of packages, and apt-get install -y --no-install-recommends curl installs curl without asking for confirmation (-y) and without optional extras. rm -rf /var/lib/apt/lists/* then deletes the downloaded list to keep the image small. check_image needs curl, and so does attack step 5.

(3) Line 4, WORKDIR /app, makes /app the folder every later instruction works in, creating it first.

(4) Lines 5 and 6 copy requirements.txt into the image and install the four packages. --no-cache-dir stops pip from keeping a second copy of every download inside the image. The packages go in before the Python files on purpose, because Docker saves the result of each instruction as a layer and keeps the layers in its build cache. When you change a .py file and build again, Docker reuses every cached layer up to the first instruction whose input changed, so the slow package install doesn't run a second time.

(5) Line 7 copies the four programs into /app. All four ride in one image. In chapter 6, Kubernetes picks which one a pod runs with a command such as gunicorn ... api:app.

(6) Line 8 creates a Linux user called app with user ID 1000. A user ID, or uid, is the number Linux uses to tell users apart. The user root is uid 0 and is allowed to do anything.

(7) Line 9, USER app, makes everything the container runs from now on run as app instead of root. That's why the injection test below shows uid=1000(app). An attacker who gets in through the bug gets only the rights of app.

Create apps/Dockerfile.news and paste this.

(1) Line 3, FROM campus-app:1.0, starts from your first image, so everything in it, the four programs and the app user included, is already there. It also means campus-app:1.0 has to be built first.

(2) Line 4 switches to root. Installing packages needs it.

(3) Line 5 installs netcat-openbsd, which provides nc, and postgresql-client, which provides psql. These are the tools a real attacker would download after getting in (ATT&CK T1105).

(4) Line 6 switches back to app, so news runs as uid 1000 like the other services.

Fire the bug at a throwaway news container

The portal isn't running yet, but you can already prove two things on your laptop. The bug in check_image works, and the commands it runs execute as the ordinary user app and not as root. A throwaway news container settles both in two minutes and leaves nothing behind.

-p 5000:5000 publishes a port, so a connection to port 5000 in Ubuntu reaches port 5000 inside the container. Everything after the image name is the command the container runs. gunicorn is the server from requirements.txt, and --bind 0.0.0.0:5000 makes it listen on port 5000 on every network interface the container has, which is what 0.0.0.0 means. Had it listened on 127.0.0.1 instead, only programs inside the container could reach it, and -p would lead nowhere. news:app tells gunicorn to load the module news, from news.py, and serve the object app inside it.

Now send the injection.

--data-urlencode "url=x; id" sends a form field called url, the same way the portal's checker form does, and it also switches curl to a POST request. curl encodes the space and the ; so they travel safely, and Flask decodes them again before check_image sees them. So check_image receives x; id, glues it onto its curl command, and the shell runs two commands, a curl aimed at a host called x and then id.
