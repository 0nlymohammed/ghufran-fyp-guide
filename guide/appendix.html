Appendix A. Plan B: an Ubuntu virtual machine

Use this appendix only if chapter 4 fails on WSL and neither its failure blocks nor chapter 13 fixed it. A virtual machine, or VM, is a whole simulated computer running inside your laptop, with its own operating system, memory and disk. Here it runs Ubuntu 24.04 Desktop, which is ordinary Linux with a desktop and a browser. Cilium then runs on Ubuntu's normal kernel instead of the WSL kernel. Expect about 2 hours for the VM, then chapters 3 and 4 again.

In the VM you work entirely inside the Ubuntu desktop. You open the guide, the terminal, the portal, the dashboard and the Hubble UI there, so localhost keeps meaning the same thing and every address in the guide stays as written. The table shows what changes.

Chapter On WSL In the VM
2 install WSL and Ubuntu, VS Code on Windows, copy files from Windows skip all of it except the Git set-up and the first commit, follow section A.5 instead
3 .wslconfig, wsl --shutdown, wsl --terminate, Docker Desktop skip .wslconfig, the wsl commands and Docker Desktop, load the kernel modules as A.5 shows, restart the VM where chapter 3 restarts the distribution

A.1 Download the Ubuntu installer

On Windows, open https://releases.ubuntu.com/24.04/ in your browser. The page offers the newest 24.04 point release. Download the desktop image for 64-bit PCs, a file named like ubuntu-24.04.5-desktop-amd64.iso, which is about 6 GB. Take a 24.04 release even if Ubuntu's main download page offers a newer one, because the guide was tested on 24.04. An ISO file is a disk image, the contents of an installation DVD stored as one file.

A.2 Create the VM on Windows 11 Pro or Education (Hyper-V)

Hyper-V is the VM program built into Windows Pro and Education. Windows Home doesn't have it, so on Home go to A.3.

  1. Press the Windows key, type Turn Windows features on or off and open it.
  2. Tick "Hyper-V", click "OK" and then "Restart now".
  3. After the restart, press the Windows key, type Hyper-V Quick Create and open it.
  4. Click "Local installation source", then "Change installation source", and pick the ISO file you downloaded.
  5. Untick "This virtual machine will run Windows (enables Windows Secure Boot)".
  6. Click "More options", type microseg as the name and click "Create Virtual Machine".
  7. When it's created, click "Edit settings". Under "Memory", set RAM to 10240 MB and untick "Enable Dynamic Memory". Under "Processor", set the number of virtual processors to 4. Under "SCSI Controller", select the hard drive and click "Inspect". The maximum disk size must be at least 60 GB. If it's smaller, close that window, click "Edit" beside "Inspect", choose "Expand" and enter 80 GB. Click "OK".

Before you start the VM, stop WSL so it gives its memory back. Chapter 3's .wslconfig lets WSL hold about 10 GB, and on a 16 GB laptop WSL and the VM can't both have that much. Run this in PowerShell.

wsl --shutdown stops every WSL distribution and the virtual machine they share. It prints nothing when it works. Then click "Connect" in the Quick Create window, and "Start" in the window that opens.

If step 2 shows "Hyper-V" greyed out, virtualization is off in the firmware. Chapter 2 shows how to check and turn it on.

If you see this instead

Hyper-V refuses to start the VM with a message that contains this text.

Usually WSL still holds the memory. Run wsl --shutdown in PowerShell again, close any programs you don't need, and click "Start" again. If it still fails, restart Windows, which frees the memory other programs hold, and start the VM before you open anything else.

A.3 Create the VM on Windows 11 Home (VirtualBox)

VirtualBox is a free VM program from Oracle that also runs on Windows Home.

  1. Download VirtualBox for Windows hosts from https://www.virtualbox.org and install it with the default choices.
  2. Open VirtualBox and click "New". Type microseg as the name, pick your ISO file under "ISO Image" and tick "Skip Unattended Installation".
  3. Under "Hardware", set "Base Memory" to 10240 MB and "Processors" to 4.
  4. Under "Hard Disk", set the size to 80 GB.
  5. Click "Finish".

Before you start the VM, run wsl --shutdown in PowerShell, as in A.2, so WSL gives its memory back. Then select microseg in VirtualBox and click "Start".

Since WSL is installed, VirtualBox has to run on top of Windows' own hypervisor. It works, only slower, and VirtualBox shows a small green turtle icon in the VM window's status bar when it runs this way. Allow extra time for image builds and the connectivity test.

If you see this instead

The VirtualBox installer stops with a message that mentions Microsoft Visual C++ 2019 Redistributable. VirtualBox needs that Microsoft library first. Download it from Microsoft at https://aka.ms/vs/17/release/vc_redist.x64.exe, run it with the default choices, then run the VirtualBox installer again.

A.4 Install Ubuntu inside the VM

The VM starts from the ISO and shows the Ubuntu installer. Choose your language, click through the accessibility and keyboard screens, and choose "Install Ubuntu". Pick "Interactive installation" and "Default selection". On the disk screen choose "Erase disk and install Ubuntu". This erases only the VM's virtual disk, never your laptop's. Create your user and password, keep your time zone, and start the installation. It takes about 15 minutes. When it asks you to remove the installation medium, press Enter, and the VM restarts into Ubuntu.

A.5 Prepare the VM

Log in. You need this guide inside the VM, because the clipboard between Windows and a VM often doesn't work, so pasting from Windows may fail. On Windows, email yourself the link to this guide's Docs page. In the VM, open Firefox, sign in to your email there and open the link. Copy commands from the guide open inside the VM. Open the terminal with Ctrl+Alt+T. In this terminal you paste with Ctrl+Shift+V, as in chapter 0.

On WSL, .wslconfig told Windows to load the kernel modules Cilium needs. In the VM you load them through a file that Ubuntu reads at every start.

printf prints the seven module names, one per line, because \n means a new line. sudo tee writes them into /etc/modules-load.d/cilium.conf, in a folder only the administrator may write to, and also prints them. Ubuntu loads every module named in this folder when it starts. Type your password when sudo asks for it. Nothing shows while you type.

You should see the seven names repeated back, one per line, in this order: xt_socket, xt_TPROXY, xt_mark, xt_CT, cls_bpf, sch_ingress and xt_recent.

Now load them once by hand, so you don't have to restart, and check two of them.

modprobe -a loads every module named after it. lsmod lists the loaded modules and grep -E '^xt_(TPROXY|socket)' keeps the lines that start with either of the two names check-env.sh tests.

You should see two lines, one starting xt_TPROXY and one starting xt_socket. The numbers after them vary by kernel.

Install VS Code, which chapter 2 otherwise installs on Windows.

snap is Ubuntu's app installer. --classic lets VS Code reach your whole home folder, which an editor needs.

You should see a line that starts with code and ends in installed. The version in the middle differs.

Then make the project folder and open it in VS Code, as chapter 2 does on WSL.

You should see a VS Code window open on the empty microseg folder. The terminal itself prints nothing, or a short notice from VS Code. Inside the VM the window title shows microseg without the [WSL: Ubuntu-24.04] part from chapter 2.

If you see this instead

The module name is misspelled. Names are case-sensitive, and TPROXY is in capitals. Copy the command again.

The name is right, but this kernel keeps the module in a separate package that isn't installed. Install it with sudo apt install -y linux-modules-extra-$(uname -r), where $(uname -r) puts in the version of the running kernel, then run the modprobe line again.

Snap is still setting itself up after the first start of Ubuntu. Wait two minutes, then run it again.

A.6 Follow the guide with these changes

Your WSL files stay in WSL. Create every file again in the VM from the chapters, as if you were starting fresh. From here, work through the guide from chapter 2's Git section onward. For the hello.txt drill in chapter 2, open the Text Editor in Ubuntu, type copied from Windows, and save it as hello.txt in the microseg folder, so the checkpoint matches.

In chapter 3, skip every step about .wslconfig, every wsl command and the paragraph about Docker Desktop. In chapter 3's systemd check, only the first line, systemd, matters in the VM. The message cat: /etc/wsl.conf: No such file or directory is expected there, so don't create the file. Where chapter 3 restarts the distribution after sudo usermod -aG docker $USER, restart the VM instead with sudo reboot. After the restart, open the terminal and run id -nG, which lists the groups your user belongs to. docker must be among them. If the check-env.sh line about 9 GB of memory prints FAIL, shut the VM down, raise its memory to 11264 MB and start it again. The check's name mentions WSL, but it measures whatever Linux runs on.

Where chapters 8, 10 and 14 send the attack from PowerShell, use these five commands in the Ubuntu terminal instead. They carry the same payloads, and curl replaces curl.exe.

You should see, on the flat network, the same answers as the PowerShell commands in chapter 8. Check the proof text of each step. Step 1 shows uid=1000(app), every scan line of step 2 contains succeeded, step 3 ends with (4 rows), step 4 shows UPDATE 1 and step 5 contains password_hash.

In chapter 14, set up Ubuntu's Terminal for screenshots instead of Windows Terminal. Click the menu button with three lines at the top right of the Terminal window and choose "Preferences". Click your profile on the left, which is called "Unnamed" unless you renamed it. On the "Text" tab, tick "Custom font" and set the size to 14. On the "Colors" tab, untick "Use colors from system theme" and pick a light scheme under "Built-in schemes", such as "GNOME light".

Capture each attack step with the terminal wrapper instead of the PowerShell blocks, for example clear; { date; curl -s http://localhost:30080/news/check-image --data-urlencode "url=x; id; hostname"; date; } 2>&1 | tee ~/microseg/evidence/E13-step1.txt. For screenshots, press the Print Screen key. A bar appears at the bottom of the screen with three choices, "Selection", "Screen" and "Window". For a terminal capture pick "Window", click the terminal, then click the round capture button. For a browser page pick "Screen" instead, so the clock in Ubuntu's top bar is in the picture. Ubuntu saves each picture in ~/Pictures/Screenshots under a name with spaces in it, such as Screenshot From 2026-11-20 14-03-22.png. Move the newest one into the evidence folder under its evidence name.

ls -t lists the screenshots newest first, head -1 keeps the first line, and $( ) puts that file name into the mv command. The double quotes keep the spaces in the name together. Change E03-nodes for each capture. mv prints nothing when it works. Skip the Windows evidence folder and the copy step of chapter 14.

The VM can't write to a Windows folder, and Hyper-V doesn't pass USB sticks through to a Linux VM, so the weekly backup from chapter 2 and your evidence reach Windows through a cloud drive. Make the archive in your home folder in the VM.

This is chapter 2's backup command with the archive written to your home folder instead of a Windows folder. It includes ~/microseg/evidence, so the same file carries your screenshots and text outputs. It prints nothing when it works. Open Firefox in the VM, sign in to your OneDrive or Google Drive, and upload the .tar.gz file from your home folder. On Windows, download it from the same drive, right-click it in File Explorer and choose "Extract All" to get the files for your thesis.
